# Proxy-Metric Health & Analytics Investment Prioritization

## What this is

A stock-take of the analytics program itself, built for whoever owns the analytics platform (RevOps, data leadership). It doesn't report a business number — it reports on the roughly dozen-and-a-half predictive models and diagnostic tools this company has already built, answering two questions: is the early-warning watchlist those tools have already flagged actually being watched, and if the next unit of analytics investment could close one gap in what the underlying data can support, which gap should it be. The honest answer to the first question today is: not yet, not in any way that can prove a trend. Most of these tools have only been checked once or twice, never on a real recurring cadence, so no tool in this portfolio — this one included — can yet say a model's accuracy is declining. This asset states that plainly rather than dressing up two data points as a trend line, and focuses instead on what can honestly be delivered right now.

## Why it exists

As the analytics program has grown past a dozen built tools, each one has already named its own specific thing worth keeping an eye on going forward — a model's accuracy slipping, a control group losing its footing, a rule that had been reliably firing going silent. Those signals live scattered across more than a dozen separate technical write-ups, which means a signal one tool has already flagged as worth watching can quietly get lost simply because nobody is looking at all of them in one place. Separately, the metric tree the whole program is built around has real gaps in what today's data can actually support, and those gaps aren't all equally worth fixing — some need a full new data-collection effort, and some are already solved by a different tool in the portfolio and simply haven't been connected yet. This asset exists to put both of those pictures — the watchlist, and the gap priorities — in one place, so nothing gets lost and the next investment goes to the highest-value, cheapest-to-close item first.

## How it works

Each time this runs, it pulls the watchlist directly from every other analytics tool's own technical documentation — not a fresh judgment call, but an inventory of what each tool has already said, in writing, is worth watching. It then checks that watchlist against a shared log every tool in the program writes real, dated results to, counting exactly how many genuine readings each watchlist item has on record today — frequently very few, occasionally none. Separately, it walks the metric tree looking for every place today's data genuinely can't answer a question the tree asks, groups those gaps by their real underlying cause, and sorts them first by how cheap they'd be to close and second by how many downstream results closing them would unlock — so the ranking points at the cheapest, highest-value fix first rather than the loudest one.

## Key decisions and why

- **A plain catalog-and-reconciliation approach was deliberately used rather than a fitted trend- or change-detection model.** With only one to three real readings behind almost every tool so far, a model built to detect a shift over time would either be mathematically undefined or would mistake ordinary noise for a real pattern. Every question this asset answers today — what's already been flagged, how many readings does it really have, which gap blocks the most evidence — already has an exact, checkable answer, so a straightforward accounting is the honest choice, not a simplified stand-in for something more sophisticated.
- **The thin-history finding is stated as the headline, not buried as a caveat.** Fabricating a longer track record to make the program look more mature than it is would trade an honest, if unflattering, picture for a false one — the same discipline this program applies elsewhere when a result comes back weaker than hoped.
- **This asset reads only the analytics program's own already-recorded state — its technical write-ups, its shared results log, and how its tools are currently wired to each other — never any customer or business data.** There is no business question at stake here, only oversight of the rest of the program, so grounding every finding in the program's own documentation and logs is what keeps this catalog honestly derived rather than independently invented.
- **Gaps in the underlying data are ranked first by cost to close and second by how much evidence closing them would unlock, using curated judgment about cost that gets re-checked against the live system every time this runs.** A gap that's cheap and unlocks a lot of value should always outrank one that's either expensive or narrow, and re-checking against the live system every run means the ranking can't silently go stale if the tools it's judging change underneath it.
- **Tools whose own documentation says ongoing monitoring genuinely doesn't apply to them, and the one tool still being built elsewhere in parallel, are called out by name rather than silently left off the list.** That keeps "deliberately not tracked" clearly distinct from "simply forgotten," which matters for a catalog whose whole purpose is making sure nothing falls through the cracks.
- **This asset checks itself with three exact reconciliation checks rather than a statistical accuracy score.** Nothing here is a prediction, so the right bar is whether the catalog is a true, current reflection of what the program's other tools actually document and actually log — not a confidence percentage, which would imply a kind of uncertainty that doesn't apply to a straight factual accounting.

## What drives the result

- **The watchlist itself** — every specific signal a built analytics tool has already named, in its own documentation, as worth watching for signs of decay: 26 of them, drawn from 15 already-built tools, assembled rather than invented
- **How many real readings each watchlist item actually has** — counted directly against the shared results log the whole program writes to, at or before the date being checked
- **The data-gap ranking** — every place the metric tree currently can't answer a question it's supposed to, grouped by root cause and sorted from cheapest-and-highest-value to most-expensive-and-narrowest
- **Two self-checking guardrails** — a check that every listed watchlist item still matches real wording in its source tool's documentation, and a check that every listed data gap still genuinely exists in the live system, so this catalog can't quietly go stale relative to what it's supposed to be describing

## Current result

As of December 31, 2025, 18 tools in the program (17 already-built analytics tools plus this one) have logged at least one real, dated result — and every single one has only one, two, or three of them, spanning at most three real dates apiece, all produced inside a single build effort rather than a real month-over-month operating cadence. Running the same check six months earlier, at June 30, 2025, only 14 of those 18 tools had any logged result yet at all, and 7 of the 26 watchlist items had zero — a materially thinner picture than today's, which is itself the clearest evidence of how new this program still is.

Of the 26 watchlist items, 3 have exactly zero real readings on record today, in every case not because the underlying tool lacks the information but because that specific number was simply never wired into the shared log — a cheaper, nearer-term fix than waiting for more history to accumulate.

The run also carries a standing cross-check between the metric tree and the marketing-attribution tool. Attribution computes and independently validates how much pipeline the marketing funnel generates, by channel; the cross-check confirms every tree item attribution covers is marked as computable in the variance engine, and it reports zero mismatches today. A mismatch would mean a gap is being described as needing new data collection when a different tool has already closed it.

Looking at every place the metric tree currently can't answer a question, sorted from cheapest-to-fix to most expensive: no gap is currently solved elsewhere and merely unconnected; one gap just needs existing raw data exposed through a proper reporting table (channel-level cost per lead and per sales meeting, where both the cost and the activity counts already exist and only the joining table is missing); one gap needs a small code fix to an existing tool (fixing how the account health score defines its scored population over time, so it can be read as a monthly series); ten gaps genuinely need new data collection or a change to how the data is generated, and together block 19 results, led by the missing web-traffic and competitive-intelligence sources, the customer-engagement funnel stages, an estimate of how much of a customer's workflow runs outside the product, the reasons customers churn, and a stage-by-stage deal history in which lost deals actually stop partway; and two items turn out not to be real, separate gaps at all, since each is already folded into a number reported one level up. Fourteen gaps remain in total, and the cheapest category holds a single item. Every top-level measure has a computable value; the remaining gaps sit one and two levels below the headline scorecard.

All three of this asset's own correctness checks pass at both checkpoints run so far (June 30 and December 31, 2025): the watchlist matches real wording in each tool's own documentation, every listed data gap is confirmed still genuinely open in the live system, and its own reading counts reconcile exactly against an independent, from-scratch read of the same shared log. Separately, this run also surfaces where the program's independent review is thinnest: of the 15 built tools with a stated threshold, only 1 has had that threshold independently confirmed by a second reviewer so far; the other 14 are still first-pass, self-proposed numbers awaiting that review — a concrete backlog, not a criticism of any one tool.

This asset becomes genuinely more useful exactly as the rest of the program starts getting checked on a real recurring cadence rather than once or twice inside a single build effort — right now, its most valuable job is reporting honestly on how thin that history still is.

## Known limitations

- **This asset cannot make the three currently-invisible watchlist items visible by itself.** Closing each one needs a small code change inside that specific tool's own logic, which is outside the scope of a catalog that only reports on what other tools have already logged.
- **The cost-to-close ranking on each data gap is a curated judgment call, not something derived automatically from the tree.** Every run reconfirms that a cited gap still exists and is still genuinely unresolved, but it can't independently reconfirm that the cost estimate itself — "this just needs a reporting fix" versus "this needs brand-new data" — is still accurate if the underlying systems change; that would need a fresh human review.
- **The specific, formally documented way this program intends to check for a metric quietly losing its grounding — comparing correlation strength before and after a stretch of time — has never actually been run once, for any real relationship in the tree.** Every one of the 26 watchlist items today instead uses that tool's own improvised version of "is this still real," and building the real, documented version is the single highest-priority open item this catalog itself surfaces.
- **No historical snapshots exist of the source documentation or the underlying data map**, so the watchlist and the gap ranking can only ever describe the program as it stands right now — unlike the reading-count reconciliation, they can't be queried for what they looked like at an earlier date.
- **This asset does not do the recurring watching itself.** It builds the list of what's worth watching and the priority order for closing gaps; running that watch on a real cadence going forward is separate work this asset deliberately leaves open rather than claiming to already do.
