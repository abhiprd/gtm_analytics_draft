# Data Quality & Metric Governance

## What this is

A structural integrity check on the analytics stack itself — it answers "can leadership actually trust the numbers the tree and the marts are producing right now," not "what do the numbers say." It's built for whoever owns the analytics platform (RevOps, data leadership) as the thing that runs before every other reported figure is treated as safe to build on.

## Why it exists

Every other asset in this portfolio — the metric tree, the health score, the forecast, the readout — assumes the underlying data and formulas are correct. That assumption is never automatically true: a formula that's supposed to tie a top-line number exactly to its sub-drivers can quietly stop tying out after a change to how the data is built; a forbidden category value can slip back into a field that's supposed to allow only three; a score that's supposed to reflect a real business driver can end up behaving like a coin flip without anyone noticing until much later. None of these failures are loud. A dashboard built on top of a silently broken formula still renders a chart — it just renders the wrong one. This tool exists to catch that class of problem before it reaches leadership, by mechanically re-checking the promises the rest of the platform is built on rather than trusting that they still hold.

## How it works

Each time it runs, the tool checks three different kinds of promise against the live, current data. First, it walks every place in the metric tree where a top-line number is defined as the sum, product, or ratio of specific underlying pieces, and confirms the built data actually adds up that way in real dollars and real percentages — not as a design intention, but as an arithmetic fact checked fresh each run. Second, it re-runs the same category of quality checks the raw source data already goes through — are the right records linked to each other, are required fields actually filled in, do values fall in sane ranges, is there enough volume to be meaningful — but this time against the finished, transformed tables leadership's reports actually pull from, since a transformation step could introduce a problem that raw-data checks would never see. Third, it turns a set of hard business rules that are supposed to always hold — segment naming stays within its three allowed values, accounts never get demoted to a lower segment, all figures are in a single currency, acquisition channel and segment never get treated as if one implies the other, all four reasons an account can change segment genuinely show up in the data — into automatic checks against live data, and adds a handful of spot-checks confirming that scores meant to reflect real business drivers, like win probability and churn risk, actually move together with the drivers they claim to reflect rather than floating independently. Everything is a direct, deterministic comparison against numbers the platform has already produced — nothing here is estimated or fitted, so there's no accuracy percentage in the ordinary sense, only a pass or a fail on each individual promise.

## Key decisions and why

- **Every check is a direct calculation against known-correct answers, not a statistical model.** Most of what this tool checks is an exact, already-stated rule — a formula the tree defines precisely, a rule like "only three segment names are ever valid." Fitting a model to detect deviation from a rule that already has one correct answer would trade a certain check for an uncertain one, for no benefit.
- **A model that flags unusual-looking values by comparing them to historical norms was considered and set aside, because there isn't yet a history to compare against.** This is the first time this kind of check has ever run, so there's no track record of "normal" yet to measure a new result against. That kind of comparison becomes valuable once enough checkpoints accumulate over time — that ongoing monitoring is handled separately by the tool responsible for tracking model performance over time, not by this one.
- **This is a distinct job from the tool that watches a predictive model's accuracy decay over time.** That tool asks whether a model that was once accurate has started to slip. This tool asks a different and more basic question — does the data actually satisfy the structural promises it always claimed to, right now. A failure caught here is a defect to go fix immediately, not a trend to keep an eye on.
- **Wherever a promised calculation genuinely can't be checked from available data, that's stated explicitly by name rather than silently left out.** A handful of the tree's formulas depend on data that doesn't exist anywhere in the underlying system — cost and compensation figures chief among them. Rather than skip those silently, each one is listed along with the specific reason it can't be checked, so a gap reads as a known, named limitation rather than an unexplained absence.
- **Where a calculation is already independently checked by another tool in the portfolio, it's referenced rather than recalculated a second time.** Re-implementing the same formula twice in two different places risks the two copies quietly drifting apart from each other over time, which would be a worse outcome than simply pointing to where the real check already lives.
- **The tool's own reliability is verified by deliberately feeding it broken, hand-built examples of every failure type it claims to catch — a mismatched formula, a forbidden category value, an illegitimate segment demotion, a genuinely random score — and confirming it correctly flags every single one as broken.** A governance tool that can't be shown to actually catch the failures it claims to guard against isn't proven to work, no matter how clean the real data currently looks. This is treated as the tool's real correctness bar, since nothing here produces an accuracy score in the usual sense.
- **The specific thresholds this tool uses — like the minimum number of times a rare data category must appear to count as genuinely present, rather than a fluke — are the tool's own first-pass judgment calls, not numbers handed down from an existing standard.** They're deliberately set well below what's currently observed in the data, so ordinary variation in future data won't accidentally trip them, while still being tight enough to catch a genuine regression. They're flagged explicitly as first-pass proposals awaiting independent confirmation, not treated as settled.

## What drives the result

- **Formula integrity checks** — every place the metric tree states that a top-line number equals a specific sum, product, or ratio of its parts, checked against real current values
- **Data quality checks on the finished tables** — whether records link to each other correctly, whether required fields are filled in, whether values fall within sane bounds, and whether there's enough data volume to be meaningful, all run against the transformed tables reports are actually built from
- **Business-rule checks** — segment naming, no segment demotions, single-currency figures, acquisition channel staying independent of segment, and all four legitimate reasons an account can change segment actually appearing in the data
- **Driver-reality spot-checks** — confirming that win probability, churn risk, and usage growth each move together with a real, stated business driver rather than behaving like noise dressed up as a signal
- **A self-test suite** — a set of deliberately broken, hand-built examples that confirm the tool actually catches each type of problem it claims to catch

## Current result

As of December 31, 2025 (with a second check six months earlier, June 30, 2025, confirming the same clean result): every one of the 53 real-data checks passes — every formula the metric tree states ties out exactly in the built data (the handful that genuinely can't be checked from available data are named individually rather than silently skipped), every data-quality check on the finished tables passes, and every business rule holds with zero violations found anywhere in the live data. All 10 of the deliberately-broken self-test scenarios are also correctly caught as broken, confirming the tool's checks actually work rather than just looking clean because nothing has gone wrong yet.

## Known limitations

- **This has only ever been run twice, and both times against data with nothing wrong in it.** A governance check that has never yet caught a real, live problem hasn't been proven against one — the deliberately-broken self-test scenarios are the stand-in evidence that the mechanism works, not a substitute for eventually watching it catch something real.
- **Several of the specific thresholds this tool uses are first-pass judgment calls, not independently derived or statistically validated numbers.** They're stated openly as proposals awaiting a second, independent review rather than presented as settled standards.
- **This tool checks the finished, transformed tables — it doesn't re-check the raw source data**, since that layer already has its own dedicated quality process upstream; re-running the same checks a second time here would add duplication rather than genuine additional protection.
