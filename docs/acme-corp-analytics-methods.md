# Acme Corp — Analytics methods

The Phase 4 equivalent of `acme-corp-gtm-metric-tree.md`: the source of truth for how each analytics artifact is built, what it's validated against, and when its performance has degraded enough to warrant review. Filled in as each artifact is actually built, per the build spec's priority order — not written speculatively ahead of the work.

An entry with no methodology yet is marked TBD, not omitted — the artifact's existence and its place in the priority order are already fixed by the build spec even before its method is chosen.

---

## Point-in-time discipline (applies to every entry below)

Every model in this doc must be computable as of any historical date using only data that existed up to that date — no leakage from the future. This is what makes backtesting and drift detection possible at all; see `analytics-engineering-conventions` for the coding rule this implies.

Historical performance is stored as a monthly time series, not sparse hand-picked checkpoints — `fact_model_performance_history` (model_name, as_of_date, metric_name, metric_value), an append-only log rather than a cross-cutting business mart. Any specific comparison ("today vs. a year ago") is a query against this series, not a separately-run one-off computation.

## Proxy-metric decoupling — general rule, applies to any Layer-3-to-Layer-2 relationship in the tree

A leaf is decoupling from its parent when the trailing 6-month correlation between them drops more than 30% relative to its trailing 12-month baseline, **while the leaf's own raw value has not declined**. That second condition is what distinguishes real decoupling (more meetings, not more wins) from a leaf simply falling off on its own (fewer meetings, naturally fewer wins) — the latter isn't decoupling, it's just decline, and the existing variance-diagnostic engine already handles it.

## Drift review trigger — general rule

Flag for review on **2 consecutive monthly checkpoints** below a stated threshold, never a single reading. One bad month is noise; two is a pattern. This applies uniformly — a specific entry below states its threshold, not a different consecutive-breach rule.

## Account health score / churn-risk model

- **Built**: `dbt/models/marts/marts/mart_account_health.sql` (grain: one row per account_id per month; joins `fact_usage_monthly`, `fact_support_tickets`, `fact_product_logins`, `fact_am_activity`, `fact_subscriptions`, `dim_accounts` so the model reads a single mart) + `analytics/health_score.py` (logistic regression, scikit-learn, `class_weight='balanced'`, seeded via `_RANDOM_SEED = 42`).
- **Model choice and why**: logistic regression, not a more complex classifier (random forest, gradient boosting, a neural network) — three reasons, all tied to this artifact's actual requirements rather than a default pick. (1) Every coefficient is directly attributable to one input feature, which is what makes the relative-importance breakdown and full coefficient table below possible without a secondary explainability technique (SHAP, permutation importance) standing between the model and its own explanation — this artifact needs to be independently auditable, not just accurate. (2) At this dataset's scale (~7,700 accounts, 15 model inputs after encoding), a linear model is a well-justified baseline; a higher-capacity model risks fitting noise rather than signal without a proportionally larger or richer dataset to justify the added complexity. (3) The score's actual downstream use is a ranking (quantile-based risk tiers, not a raw probability read literally — see the calibration note below), and a linear model's ranking behavior is more predictable and easier to sanity-check (e.g., confirming more support tickets always pushes risk in one direction) than an ensemble's. Achieving the QA plan's 0.65–0.80 AUC target with this simpler model is itself evidence the added complexity of a more powerful model class isn't needed to hit the stated bar — not a compromise made to keep things simple.
- **Inputs**: usage trend (account-relative baseline — trailing-3-month mean actions_consumed ÷ the account's own cumulative-to-date mean, not a flat trailing-month comparison), support ticket volume/severity (trailing 3 months), engagement/login frequency (reweighted per the QA plan — multiplied by 1.0 within an account's first 90 days of tenure, by 0.33 after, before being fed to the model as `login_frequency_weighted`), AM sentiment notes (trailing 3-month average `sentiment_score`, null for SMB — no-touch, no AM).
- **Why these four inputs**: usage trend, support ticket volume/severity, engagement/login frequency, and AM sentiment are the account health score's inputs by design, not by feature selection — `docs/acme-corp-gtm-metric-tree.md`'s Account health score leaf and `docs/acme-corp-gtm-portfolio-build-spec.md`'s retention/expansion mechanics both fix these four as the score's inputs at company-model-design time, before this model existed. `analytics/health_score.py` decides how much relative weight each of the four carries in the fitted decision boundary (see Relative importance in the Statistical validation package below); it does not select which signals to include from a wider candidate pool.
- **Label / point-in-time design**: one scored snapshot per account. Churners are scored `_SCORING_LEAD_MONTHS = 5` months before their actual churn month (label=1); survivors get a seeded-random scoring month drawn from their own history, at least 5 months before `as_of_date` (label=0) — a fixed "recent" snapshot for every survivor was tried first and rejected: it clustered every negative example on one calendar month, which degenerated any date-based train/test split. Held out via a class-stratified random split (`sklearn.model_selection.train_test_split`, seeded), not a temporal split — churn events concentrate earlier in the 36-month window (recent-cohort accounts haven't reached their churn point yet, ordinary right-censoring), so a late-date holdout ends up with only a handful of positives and an unstable AUC estimate. Point-in-time discipline holds regardless of split strategy: every row's features are computed only from that account's own data up to its own scoring_date, so shuffling rows across train/test cannot leak future information into any feature.
- **Target**: 0.65–0.80 AUC predicting eventual churn (QA plan grounding target). **Achieved: 0.7613 holdout AUC** (as_of_date 2025-12-31, n_train=5,277, n_test=1,760), logged to `fact_model_performance_history` via `analytics/model_performance.py`.
- **Calibration note (load-bearing, not incidental)**: `generators/config.py`'s `DECLINE_MONTHS_BEFORE_CHURN = 4` is how many months before churn the generator's deterministic usage/ticket/sentiment decline window starts. Scoring at or inside that boundary (`_SCORING_LEAD_MONTHS <= 4`) lets the model see the designed collapse directly and produced an inflated, unrealistic 0.93–0.99 AUC during build — pattern-matching the generator's own construction, not a genuine early-warning signal. `_SCORING_LEAD_MONTHS = 5` (one month before the decline window starts) is what actually exercises an early-warning problem and is what the 0.65–0.80 target describes.
- **Drift threshold**: AUC below 0.65 for 2 consecutive monthly checkpoints → flagged for review
- **Test E validation (QA plan)**: "High-automation, low-login, high-Actions accounts exist and are NOT predominantly mis-flagged as at-risk" — confirmed. Cohort defined per-segment as top-quartile trailing Actions AND bottom-quartile trailing logins (557 accounts as of 2025-12-31). `risk_tier` is quantile-based over the scored active population (top 20% = High) rather than a fixed probability cutoff — `class_weight='balanced'` shifts predicted probabilities up systematically, so a fixed 0.5 cutoff mis-flagged ~72–91% of accounts as High regardless of cohort. Under quantile tiering: population High-risk rate 20.0%, automated-but-healthy cohort High-risk rate 19.7% — at parity with, not elevated above, the general population.
- **Statistical validation package** (as_of_date 2025-12-31, computed on the same 1,760-row held-out split the holdout AUC above is computed on):
  - **Relative importance**: each of the twelve numeric model features is mapped to its one conceptual input (`_CONCEPTUAL_INPUT_GROUPS` in `analytics/health_score.py`), coefficient magnitudes are summed within each of the four groups, and the four group sums are normalized to 100%. `tenure_days`, `is_within_first_90_days`, and one-hot `segment` are excluded from this breakdown entirely (not folded into any group, not given a fifth bucket): they are real model features but not one of the four conceptual inputs this breakdown answers for, and `segment`'s dummy encoding is not on the same scale as the standardized numeric features, so including it would not be a like-for-like comparison. **Result: AM sentiment 34.7%, usage trend 32.0%, ticket volume/severity 27.2%, login frequency 6.0%.** Two caveats travel with this figure: (1) the AM sentiment group's weight is carried almost entirely by whether an account has any AM activity at all in the trailing window (`has_am_activity_3mo`, coefficient −0.322), not by the sentiment score's own polarity (`am_sentiment_avg_3mo`'s coefficient is −0.001, essentially zero) — this partly reflects which accounts have AM coverage at all (SMB has none) rather than sentiment content specifically. (2) `login_count_avg_3mo` and `login_frequency_weighted` are two representations of one underlying login signal (the second is a tenure-reweighted transform of the first), so the login-frequency group's percentage reflects the model's combined reliance on login behavior rather than two independently-contributing signals. Coefficient magnitude on jointly-standardized features is a defensible relative-importance heuristic for a linear model, reflecting the model's own reliance on a signal within its fitted decision boundary — not an independently-estimated, real-world causal effect size.
  - **Coefficient table** (standardized scale — `StandardScaler` applied to all 12 numeric inputs before fitting, so these are relative-magnitude comparisons, not raw-unit effects; sorted by absolute magnitude):

## Segment/segmentation migration analysis

- **Built**: `dbt/models/marts/marts/mart_segment_migration.sql` (grain: one row per migration event -- excludes each account's initial segment-history row -- joined against `int_account_segment_spans` for `days_in_prior_segment` and `int_revenue_movements` for `mrr_reclassified`) + `analytics/segment_migration.py`, which reads `mart_segment_migration` for event detail, `mart_durability` for segment population denominators (migration-rate calculations), and `mart_growth_bridge` for an independent cross-check on graduated revenue (not a competing computation -- both marts derive from the same `int_revenue_movements` rows upstream).
- **Shape decision -- structural/descriptive, not predictive**: this artifact computes migration velocity/rate by segment pair and `trigger_reason`, confirms `firmographic_rescore` migrations actually fire (not just `usage_threshold`), time-in-prior-segment distributions, and "graduated revenue" (MRR reclassified out of the source segment via migration, per the build spec's exclusion of migration from source-segment churn/contraction). None of that is a prediction task -- it is a direct, deterministic aggregation of `mart_segment_migration`'s already-computed event rows. Per `analytics-engineering-conventions`' "Structural/logic artifacts" category (named there for the variance-diagnostic engine, applied here on the same reasoning): no coefficient table, no AUC, no confusion matrix, no R²/RMSE -- forcing any of those onto a population-level descriptive summary would be theater, not rigor. This is stated explicitly rather than left as TBD fields.
- **Model type selection and rationale (why not predictive)**: a migration-propensity/readiness classifier (analogous in shape to the account health score's churn-risk model) was considered and rejected as a genuine fit for this artifact. SMB->Commercial and Commercial->Enterprise migration in this data is generated from a known, largely deterministic rule -- usage/spend crossing a threshold for 2 consecutive months, with noise -- plus an exogenous firmographic re-score path. A classifier trained on usage trend to "predict" migration would mostly be re-deriving the generator's own threshold rule, the same trivial-accuracy failure mode the health score's calibration note explicitly documents and guards against for churn scoring (scoring too close to a deterministic decline window inflates AUC to ~0.93-0.99, which measures pattern-matching the generator's construction, not a genuine early-warning signal). A real predictive segmentation/scoring artifact already has its own place in the portfolio -- build spec item #11, "Lead/segmentation scoring -- model validation & drift detection" (Wave 7, its own methods-doc entry below, still TBD) -- and is not duplicated here.
- **Inputs**: `mart_segment_migration` (`account_id`, `from_segment`, `to_segment`, `migration_date`, `trigger_reason`, `days_in_prior_segment`, `mrr_reclassified`); `mart_durability` (`segment`, `month`, `starting_accounts`) as the population denominator for migration rate; `mart_growth_bridge` (`segment`, `month`, `migration_in_mrr`, `migration_out_mrr`) for reconciliation only.
- **Point-in-time design**: every function takes `as_of_date` and filters to `migration_date <= as_of_date` (or `month <= as_of_date` for the population/reconciliation marts) -- no leakage from the future. Migration velocity and graduated revenue are computed over a trailing 12-month window ending at `as_of_date` (`_DEFAULT_WINDOW_MONTHS = 12`); trigger-reason mix and time-in-prior-segment distributions are computed all-time-to-date as of `as_of_date` (sample sizes are thin enough per trailing window that an all-time-to-date view is the honest one for a distributional read; both respect the same `as_of_date` cutoff). No stochastic step exists anywhere in this module (no train/test split, no sampling, no simulation), so no random seed applies.
- **Validation in place of a predictive target** (computed `as_of_date` 2025-12-31, full history back to 2020-01):
  - **Growth-bridge reconciliation** (structural correctness invariant, not a statistical estimate): summing `mart_segment_migration.mrr_reclassified` by `to_segment`/month (migration-in) and by `from_segment`/month (migration-out) and comparing against `mart_growth_bridge`'s independently-materialized `migration_in_mrr`/`migration_out_mrr` for the same segment/month. **Max absolute diff: $0.00 (2.9e-11, floating-point noise only)** -- reconciles exactly, as expected since both marts share `int_revenue_movements` as their upstream source. A future diff beyond $0.01 would indicate a real bug in one of the two marts, not model drift.
  - **Trigger-reason diversity existence check** (QA plan requirement: `firmographic_rescore` migrations "must actually fire... not just as a schema value that never occurs"): **firmographic_rescore share -- 30.3% overall (245/809), 28.9% within SMB->Commercial (209/722), 41.4% within Commercial->Enterprise (36/87)**. All three comfortably clear the proposed floor below.
  - **Sample sizes**: 809 migration events total as of 2025-12-31 (722 SMB->Commercial, 87 Commercial->Enterprise); trailing-12-month window has 437 and 65 events respectively -- both large enough for the rate/distribution reads above to be more than single-digit-N noise.
- **Target / floor (CONFIRMED by `analytics-model-validator`)**: no accuracy/error target applies (structural/descriptive, per the shape decision above). Two grounded floors apply in its place, in the same spirit as the health score's stated AUC target but newly derived here since the QA plan gives no number for either:
  1. **Growth-bridge reconciliation tolerance: max abs diff <= $0.01.** Not really "proposed" so much as a hard structural invariant given both marts share their upstream source -- included here because the doc's point-in-time-discipline section asks every entry to state a target explicitly, not because there is genuine uncertainty about what the right number is.
  2. **Firmographic-rescore share floor: >= 10% of migrations, both overall and within each segment pair.** Grounded the same way the QA plan's "non-trivial frequency" language is meant, quantified: 10% is unambiguously non-trivial (far above 0%, i.e., real evidence the trigger path fires under realistic generator conditions) while leaving comfortable headroom below the ~29-41% observed at build time, so ordinary period-to-period variation in future checkpoints won't spuriously trip it. This number was not specified anywhere upstream (build spec, QA plan, metric tree) -- it was this artifact's own proposal at build time. `analytics-model-validator` independently checked it against sampling noise on the thinnest segment-pair sample (Commercial->Enterprise, trailing-12-month n=65: binomial standard error ~6.1pp, so even a 2-sigma bad month sits around ~29%, well clear of 10%) and confirmed it as a defensible floor -- not trivially trippable by ordinary variation, still far enough below the observed range to catch a real regression. May reasonably tighten toward 15-20% once more monthly checkpoints accumulate in `fact_model_performance_history`; no basis to do so yet on this single build-time snapshot.
- **Drift review trigger**: per the doc's general rule, 2 consecutive monthly checkpoints below either floor above -> flagged for review. In practice the reconciliation floor is expected to never breach (structural invariant); the firmographic-rescore share floor is the one worth actually watching in `fact_model_performance_history` (`pct_firmographic_rescore_overall`, `pct_firmographic_rescore_smb_to_commercial`, `pct_firmographic_rescore_commercial_to_enterprise`) as more of the timeline accumulates.
- **AM ownership migration** (build spec: "Segment migration also migrates AM ownership... typically opening a renewal/expansion opportunity"): out of scope for this artifact as built -- the analysis here is revenue/event-pattern-focused (velocity, trigger mix, time-in-segment, graduated revenue). AM-ownership continuity at migration is not currently exposed by any `mart_*` table this module is allowed to read from, so it isn't asserted here one way or the other; confirming it would need a Phase 2 mart change, not a Phase 4 workaround.
- **Persistence**: scalar time-series metrics (migration counts/rates by segment pair, firmographic-rescore share overall and by segment pair, graduated-revenue MRR by segment pair, median days-in-prior-segment by segment pair, reconciliation max-abs-diff) are logged to `fact_model_performance_history` via `analytics/model_performance.py`'s `log_performance()`. The full trigger-reason-mix table, time-in-prior-segment distribution table (mean/median/p25/p75/min/max), and graduated-revenue-by-trigger-reason breakdown are NOT logged there (variable-width tables don't fit that log's flat scalar grain, per `analytics-engineering-conventions`' Persistence note) -- they are the structured detail recorded in this entry instead.

## Marketing attribution & channel mix

- **Built**: `analytics/marketing_attribution.py`. Grain: one row per lead per attributed sub-channel per attribution model — every published table (channel mix, the cross-model mix shift, the Pipeline-generated decomposition, the Layer-3 diagnostics, the incrementality read) is an aggregation of that credit panel, which is itself built on a one-row-per-touch sequencing table derived in this module. No dbt model was added or changed for this artifact, and no Phase 1 generator or raw table was added; campaigns, leads, campaign touches and the holdout cells all already exist as real generated data.
- **What it is**: build spec item #6, the third Wave 2 artifact. It makes the metric tree's **Pipeline generated** branch computable at the grain the tree actually defines it on — `Σ over channels (channel volume × channel-to-lead rate × lead-to-PQL rate)`, split into Organic/content, Paid and Community/events, each with its own Layer-3 leaves. Before this module those three Layer-2 legs had no computation behind them at all; `mart_growth_bridge`'s own header says so explicitly ("NOT built here: the Layer-2 'Pipeline generated' organic/paid/community breakdown"). **That header's stated *reason* is now stale** — it says the breakdown "needs leads/campaign-touch data that doesn't exist in this raw data... there's no leads or campaign table at all," which was true when it was written and is no longer: `dim_campaign`, `fact_leads` and `fact_campaign_engagement_events` all exist and are what this artifact runs on. The header's *conclusion* (the breakdown is not built in that mart) still stands. Correcting the comment is a one-line dbt change, deliberately not made here, and is flagged for whoever next touches that model. This artifact does not duplicate or contradict that mart's Growth-pillar math — the bridge computes New Logo from `fact_opportunities` at close, this module computes the lead-side funnel that feeds it, and the two meet at the converting lead → inbound account join.
- **Channel taxonomy**: organic / paid / community **decomposes** the `inbound_marketing` value of `dim_accounts.channel`. It is not a replacement for that field and carries no `self_serve` volume (product-led, campaign-sourced only incidentally) and no `outbound_sdr` volume (tracked under win rate, per the metric tree's own note). Nothing in this module is ever joined to `dim_accounts.channel` as if the two were the same domain.
- **Shape decision — structural/descriptive, with one design-based experimental estimator**: nothing here is fitted. Touch sequencing, credit assignment, channel mix and the Pipeline-generated decomposition are deterministic aggregations of already-materialized mart rows; the attribution weights are **stated rules, not estimated parameters**. The one estimated quantity is the holdout incrementality read, and it is a design-based (randomized-cell) estimate with a closed-form standard error — a two-proportion comparison, not a fitted model. Per `analytics-engineering-conventions`' **"Structural/logic artifacts"** category — the same reasoning the Segment migration, Variance-diagnostic engine and Capacity planning entries use — **there is no coefficient table, no R²/RMSE, no residual diagnostics, no AUC, no confusion matrix and no calibration note here, and their absence is deliberate, not pending.** Stated explicitly rather than left as blank/TBD statistics fields. This shape call was made against the data, not assumed from the artifact's name — see the next bullet.
- **Model type selection and rationale (why not a fitted attribution model)**: the credible alternatives were considered and rejected on grounds specific to this data.
  1. **A Markov / removal-effect or Shapley attribution model** — the standard "algorithmic" upgrade over rule-based MTA. Rejected because it would estimate, from observational path data, precisely the quantity this dataset already measures **causally**: six genuinely suppressed holdout cells exist (paid and community, three quarters), giving a real randomized control group. Fitting a removal effect where a real removal experiment is available would replace a causal answer with a correlational proxy for it. The honest design is to report the rule-based models for their intended purpose (how credit is *allocated*) and the holdout for its intended purpose (what is *incremental*), and to show the gap — which is exactly what this module does.
  2. **A conversion-propensity classifier on touch features** — rejected for the same reason the Segment migration entry rejected a migration-propensity classifier and the health score's calibration note guards against: `generators/marketing_funnel.py` draws touch count from a mean scaled by a `TOUCH_CONVERSION_LIFT` factor keyed on whether the lead converts, so a classifier trained on touch volume would largely re-derive the generator's own construction and report an inflated accuracy that measures pattern-matching, not signal. Also, `fact_leads.lead_score` — the obvious feature — is explicitly a terminal-state composite that reads observed engagement depth, so it leaks the outcome by construction. It is deliberately **not loaded anywhere in this module**.
  3. **A media-mix model (regression of conversions on spend)** — not rejected so much as **out of scope by the build spec's own sequencing**: MMM/incrementality is item #12, Wave 6, and the build spec already flags (Section 4) that 36 months monthly is thin for it. This artifact supplies the channel-grain spend and conversion series such a model would need, and does not pre-empt it.
- **Inputs**, all read from dbt's marts layer:
  - `dim_campaign` (`campaign_id`, `channel`, `start_date`, `end_date`, `campaign_duration_days`, `budget`, `is_holdout`) — the sub-channel taxonomy, campaign windows, day-proratable spend, and the holdout assignment.
  - `fact_leads` (`lead_id`, `account_id`, `channel`, `created_date`, `converted_date`, `is_converted`, `days_to_conversion`) — the funnel population. `lead_score` is deliberately not read (see above).
  - `fact_campaign_engagement_events` (`event_id`, `lead_id`, `campaign_id`, `channel`, `event_type`, `event_timestamp`, `event_date`) — raw touch grain, never deduplicated. `channel` here is the **campaign's** sub-channel and is not always the lead's own, which is what leaves multi-touch attribution something to attribute.
  - `fact_opportunities` + `dim_accounts` — won new-logo bookings per converting lead, and segment for the segment cut.
  - `fact_marketing_spend` + `dim_date` — the coarse-grain spend cross-check and the day-proration calendar.
  - **Read-scope note**: all six are marts-layer models in `main_marts`, per the corrected boundary in `analytics-engineering-conventions` (the layer is `dim_*`/`fact_*`/`mart_*` under `dbt/models/marts/`, not a `mart_*`-prefix-literal reading). No `stg_`/`int_`/raw source is touched.

### Touch sequencing — derived here on purpose, and why that is the point-in-time-safe place for it

`fact_campaign_engagement_events` deliberately does **not** materialize `touch_seq` / `is_first_touch` / `is_last_touch`. Its own header states why, and this artifact agrees with the reasoning rather than working around it: a whole-history window function cannot be maintained correctly by an incremental model, because a late-arriving touch silently invalidates a previously-written last-touch flag. They are also attribution decisions, not raw-stream facts.

`build_touch_sequence()` derives them from raw event timestamps, ordering on `(event_timestamp, event_id)`. `event_timestamp` is already unique within a lead — the generator forces strict ordering and `tests/assert_lead_touch_timestamps_unique.sql` enforces it — so `event_id` is a stability tie-break that never actually fires in this data, included so the sequence stays deterministic if that invariant ever weakened.

**Point-in-time safety is structural, not a filter bolted on afterwards.** The window is computed over each lead's touch history *restricted to* `event_date <= as_of_date`, so `is_last_touch` means "the last touch known at `as_of_date`." That is exactly the property that makes the derivation safe here and unsafe as a written-once dbt column: recomputing at a later `as_of_date` legitimately moves the flag to a newer touch, whereas a materialized column would keep asserting a stale answer.

**The derivation is independently checked**, which matters because the last-touch flag has nothing to verify it against. Every lead's derived first-touch campaign channel must equal `fact_leads.channel`, since a lead's sourcing campaign *is* its first touch — and this module never reads `fact_leads.channel` when building the sequence. **Result: 47,118 of 47,118 leads match at `as_of_date` 2025-12-31 (39,804 of 39,804 at 2025-06-30).** A mis-ordered sequence — wrong sort key, unstable tie-break, a late touch treated as first — would surface here immediately.

### Point-in-time conversion state — how an open lead is handled vs. a resolved one

A lead that has not converted *by* `as_of_date` is not the same thing as a lead that never converts, and collapsing the two would import future knowledge into every historical conversion rate. `build_lead_panel()` re-derives a three-valued state and never reads `fact_leads.is_converted` directly downstream:

| State | Definition | Treatment |
|---|---|---|
| `converted` | `is_converted` **and** `converted_date <= as_of_date` | The attribution population. Credit is only ever assigned for a conversion that has actually happened |
| `open` | not converted as of `as_of_date`, and fewer days elapsed since creation than its channel's observed resolution horizon | Excluded from **both** numerator and denominator of every conversion rate — counting it as a non-conversion would understate the rate purely as a function of where `as_of_date` falls |
| `lapsed` | not converted as of `as_of_date` and past its channel's horizon | A resolved non-conversion. The denominator every rate here is actually computed on |

A lead whose terminal `is_converted` is True but whose `converted_date` falls **after** `as_of_date` is `open`, never `converted` — the exact case where reading the terminal flag would leak, and the reason the panel re-derives rather than passes through. `converted_date` and `days_to_conversion` are nulled out wherever the conversion is not yet visible, so no downstream consumer can read them by accident.

**The resolution horizon is derived, not hardcoded**: the maximum observed lead-to-conversion gap per sub-channel, measured only over conversions already visible at `as_of_date`. At 2025-12-31: **organic 120 days, paid 180, community 314** (organic 84 at 2025-06-30 — the horizon is itself an as-of estimate and is stated as such). The maximum rather than a high quantile is used deliberately: mis-classifying a still-convertible lead as a resolved non-conversion would bias every conversion rate downward.

**Right-censoring is reported as a bracket, not hidden.** `lead_to_pql_rate` on a resolved-only denominator climbs toward 1.0 in the most recent periods — arithmetically correct, but a number nobody should read as a conversion rate. `compute_pipeline_generated()` therefore carries `leads_open`, `resolution_completeness`, `is_fully_resolved`, and a genuine bracket: `lead_to_pql_rate_lower_bound` (every open lead eventually fails) and `..._upper_bound` (every one converts). The bounds coincide with the point estimate exactly when `leads_open = 0`, which is the only condition under which the point estimate is unqualified. Same discipline as capacity planning's `has_opportunity_supply` flag — report the incomplete row with its incompleteness attached rather than dropping it silently.

### Attribution models — four built, one deliberately not

| Model | Weight rule | Why it is here |
|---|---|---|
| `first_touch` | 1.0 on `touch_seq = 1` | Build spec minimum. Trivial once sequencing exists |
| `last_touch` | 1.0 on the last touch **known at `as_of_date`** | Build spec minimum |
| `linear` | `1 / touches_in_path` on every touch | The build spec's "equal credit across all of a converting lead's touches." Used as the credit basis for every Layer-3 efficiency ratio, since it reflects participation across the whole path rather than one privileged position |
| `time_decay` | `0.5 ** (days_before_conversion / half_life)`, renormalized per lead | **Built because recency is a real causal mechanism in this data, not a textbook add-on.** `generators/marketing_funnel.py` places a converting lead's last touch in the final fifth of its window while a non-converting lead's touches decay away within days, so a recency-weighted model reads something the other three cannot |

**Half-life: 20 days, derived not imported** — the median observed lead-to-conversion gap over conversions visible at `as_of_date` (`derive_decay_half_life_days()`). A 7-day default (the common analytics-tool convention) would collapse community almost entirely, since community's median gap is ~54 days against organic's ~13. Using the population's own median makes the parameter a statement about this funnel rather than about a tool's defaults. It is stable across checkpoints (20 days at both 2025-12-31 and 2025-06-30).

**Position-based (40/20/40) was considered and deliberately not built.** It assigns credit to exactly the three positions `first_touch`, `last_touch` and the middle already isolate, so its channel split is a convex combination of splits this module already reports and cannot fall outside their range. It would add a row to the mix table without adding a diagnostic.

Every model normalizes to exactly 1.0 per converting lead, so conversion credit and dollar credit are attributed on identical weights and both conserve exactly — see validation.

### Channel mix, and the real shift across models

**Result at `as_of_date` 2025-12-31** (2,061 converting leads, $20,721,252 attributed won new-logo bookings):

| Channel | first_touch | last_touch | linear | time_decay | first→last shift |
|---|---|---|---|---|---|
| Organic | 48.81% | 47.74% | 47.47% | 47.53% | **−1.07pp** |
| Paid | 37.89% | 37.41% | 37.85% | 37.71% | **−0.49pp** |
| Community | 13.29% | 14.85% | 14.68% | 14.76% | **+1.55pp** |

First-vs-last **total-variation distance: 0.0155** — 1.55% of all attributed credit changes hands when the model is swapped. The mechanism behind it: **31.7% of converting leads have a multi-sub-channel touch path, and 5.77% (119 of 2,061) have a first-touch channel different from their last-touch channel.**

**This is a generator-routing artifact, not a funnel-position finding — stated first, not as a caveat that arrives after the reader has already drawn a conclusion.** `generators/marketing_funnel.py` routes a cross-channel touch uniformly across the two non-sourcing sub-channels, unweighted by channel size, touch index, or any behavioral covariate, so the smallest channel (community, 13.3% of converting leads) structurally over-receives switch-ins relative to what it sends — independent of where it actually sits in the funnel. The switching matrix:

| | → community | → organic | → paid | sends |
|---|---|---|---|---|
| **from community** | 257 | 6 | 11 | 17 |
| **from organic** | 27 | 952 | 27 | 54 |
| **from paid** | 22 | 26 | 733 | 48 |
| **receives** | **49** | **32** | **38** | |

Net flow: community **+32**, organic **−22**, paid **−10**. A size-blind null (predicted purely from each channel's share of the two larger channels' switch-outs) reproduces this pattern almost exactly (predicted +35.8 / −27.6 / −8.1), and each channel's own switch-*out* rate is nearly constant (community 6.20%, organic 5.37%, paid 6.15%) — the signature of a uniform rule, not a funnel-position effect. So: community happens to gain share under last-touch in this run, and that gain has **zero information content about funnel position** — it is fully explained by community being the smallest channel under a routing rule that doesn't know channel size exists. The mix shift is real and non-vacuous in the narrow sense that the validation check requires (the models genuinely produce different splits, confirmed distinguishable from switching noise) — but non-vacuous is not the same claim as business-meaningful, and this direction should not be read as "community closes deals other channels start." That is a limitation of what the generated data can demonstrate, not a finding about channel behavior.

Segment cut (`compute_channel_mix(segment=...)`) shows the mix is genuinely segment-dependent and not a uniform rescaling — organic 51.5% of SMB first-touch credit vs. 29.7% of Enterprise, community 10.9% of SMB vs. 35.1% of Enterprise. Channel and segment stay orthogonal per `CLAUDE.md`'s invariant: each sub-channel produces leads in all three segments, with a firmographic tilt rather than a partition.

**Bookings share diverges from conversion share, and the gap is a finding, not a rounding artifact**: paid carries 37.9% of first-touch conversions but 39.1% of first-touch bookings, and community 13.3% of conversions against 28.5% of bookings — community converts fewer, larger accounts. Both are reported side by side on every mix row.

### The metric tree's Pipeline-generated formula, made computable

`compute_pipeline_generated()` computes the tree's formula literally, per period per sub-channel plus an `All` roll-up:

- `channel_volume` = engagement touches on that sub-channel's campaigns in the period (raw touch stream, never deduplicated)
- `channel_to_lead_rate` = leads created in the period ÷ `channel_volume`
- `lead_to_pql_rate` = leads converted ÷ leads **resolved**, point-in-time
- `pipeline_generated` = the product

**Terminology, stated rather than assumed**: the tree's "PQL" terminal event is this funnel's signup/conversion — `fact_leads.is_converted`, 1:1 with an inbound-sourced account's creation. There is no separate product-qualification event in this data, so the rate is named for what it actually measures. The period is keyed on lead **creation** for the volume and rate legs and conversions are counted on those same leads, so the identity closes on a consistent cohort rather than mixing a creation-period denominator with a conversion-period numerator.

**Layer-3 leaves now computable for the first time** (`compute_layer3_diagnostics()`, long format — one row per period × channel × metric, each carrying the verbatim `metric_tree_leaf` text it computes, so the mapping can be checked rather than trusted):

| Tree leaf | Computed as |
|---|---|
| Organic traffic growth, by source (docs, blog, SEO) | `organic_traffic_{seo,docs,blog,content_asset}` + period-over-period growth, from `event_type` |
| Content publish velocity and engagement per piece | organic campaigns launched per period; organic touches ÷ campaigns |
| Docs traffic → signup conversion rate | resolved leads with a `docs_view` touch that converted ÷ all such resolved leads |
| Spend and CPL/CPC/CPM by campaign | `paid_spend` (day-prorated budget), `paid_cpl` (÷ leads), `paid_cpc` (÷ click touches). **CPM not computable** |
| Paid conversion rate (click → signup/lead) | `paid_click_to_lead_rate` and `paid_lead_to_signup_rate`, reported separately rather than conflated |
| Paid pipeline ROAS (pipeline $ ÷ spend) | `paid_bookings_roas` — **named for what it is**, see the measure caveat below |
| Community active-member growth | distinct prospects with a join/post touch + period-over-period growth |
| Event/webinar attendance and event-sourced pipeline | `event_registrations`, `event_attendance`, `event_attendance_rate`, `event_sourced_bookings` |
| Community-to-paid conversion rate (prospects) | converted ÷ resolved community-sourced leads |

**Leaves that genuinely are not computable are listed, not silently omitted** (`NOT_COMPUTABLE_LAYER3_LEAVES`, the same treatment `analytics/variance_diagnostic.py` gives its coverage gaps): *branded vs. non-branded organic split* (no keyword/query attribute on the touch stream), *SEO ranking movement* (no rank-tracking source anywhere in Phase 1), *CPM* (no impression volume — the paid event stream starts at the click). All three are Phase 1 gaps, not Phase 4 workarounds.

**Measure caveat — "pipeline" is won bookings here, and that is a real structural limit.** `fact_opportunities` carries `account_id` only on won new-business rows; all 1,191 lost new-business opportunities have a NULL `account_id`, so a lost deal cannot be traced back to the lead that sourced it. A literal "pipeline $ attributed to channel" is therefore **not computable** from this data, and the tree's ROAS leaf is reported as a *bookings* ROAS, named for what it is rather than relabelled as the leaf it approximates. Closing this would need `account_id` (or a company-level key) on lost opportunities — a Phase 1/Phase 2 change, flagged not fabricated.

### Incrementality (causal) vs. attribution (correlational) — and the gap between them

Six genuinely suppressed holdout cells exist: **paid and community, 2023Q3 / 2024Q2 / 2025Q1**. A holdout here is a real control, not a flag — its budget is withheld rather than relabelled, its leads receive fewer touches and no cross-campaign touches.

**Cell assignment is the holdout flag of the lead's first-touch campaign** — its sourcing campaign, and therefore its assignment. This is **intention-to-treat** and deliberate: crossover exists in both directions within the experiment (at 2025-12-31, 13 of 1,239 assigned-control leads later pick up a non-holdout fallback touch once their cell's window ends, and 38 of 5,026 treated leads pick up a holdout-campaign touch the same way — both figures on the same within-experiment denominator, not a dataset-wide count of incidental touches outside any holdout channel-quarter). Reclassifying either group on realized exposure would condition on post-assignment behavior, so both stay in their assigned arm — which makes the measured lift a **conservative, attenuated** read rather than an inflated one.

**Cells are pooled only once fully resolved**, and this was a real defect caught at the second checkpoint rather than a precaution. Censoring here is *informative*, not random: a converting lead resolves at its channel's median gap while a non-converting one only resolves once the full horizon has elapsed, so a recent cell's resolved subset is almost entirely converters and **both arms' rates run to 1.00**, collapsing the measured incremental share to 0 for a reason that has nothing to do with the treatment. At `as_of_date` 2025-06-30 two cells did exactly that. A cell is now evaluable only when `leads_open = 0` across both arms; censored cells are still reported at cell grain, flagged, not dropped. The evidence the fix corrects a real bias rather than just trimming an inconvenient cell is in the pre-fix numbers themselves: pooling every cell including the censored ones gives 0.6775 (2025-12-31) vs. 0.6763 (2025-06-30) — deceptively stable-looking, because a collapsed cell pulls the pooled estimate down by a roughly constant amount at both checkpoints rather than by a random one. The per-cell average of incremental shares — the statistic actually distorted by a collapsed cell — moves from 0.720 (Dec) vs. 0.495 (Jun) pre-fix to 0.730 vs. 0.743 post-fix: a large, checkpoint-dependent swing pre-fix that becomes stable once the collapsed cells are excluded rather than averaged in. That swing, not the pooled figure, is the evidence.

**Result at `as_of_date` 2025-12-31** (5 of 6 cells fully resolved; community 2025Q1 censored — its 314-day horizon does not close until 2026-02):

| Scope | Treated (resolved / conv / rate) | Control (resolved / conv / rate) | Incremental share | SE | z |
|---|---|---|---|---|---|
| **Pooled, all cells** | 4,751 / 179 / 3.77% | 1,168 / 14 / 1.20% | **0.6819** | 0.0877 | **4.43** |
| Paid | 4,380 / 146 / 3.33% | 1,107 / 13 / 1.17% | **0.6477** | 0.1013 | 3.83 |
| Community | 371 / 33 / 8.89% | 61 / 1 / 1.64% | **0.8157** | 0.1853 | 1.95 |
| Organic | — | — | **not measurable** | — | — |

**The comparison, and what it actually shows.** Both columns are scoped to exactly the same population — treated leads inside fully-resolved holdout cells — so the gap is a gap of method, not of scope:

| Channel | Attributed conversions (linear) | Measured incremental share | Implied incremental conversions | Attribution overstates by |
|---|---|---|---|---|
| Paid | 139.6 | 0.6477 | 90.4 | **35.2%** |
| Community | 34.6 | 0.8157 | 28.2 | **18.4%** |
| Organic | 4.85 (all of it cross-channel last/linear credit; **0.0** first-touch) | — | — | **not estimable** |

Three honest readings, and no reconciliation is fabricated where none exists:

1. **There is no clean reconciliation, and there cannot be one.** Attribution answers "which channel gets credit for conversions that happened"; incrementality answers "which conversions would not have happened." These are different questions with different denominators, and the module reports both rather than blending them into a single "incrementality-adjusted attribution" number that would be neither.
2. **The largest attributed channel is the one with no causal read at all.** Organic takes 47–49% of attributed credit under every model, and its incremental share is **not estimable** — `dim_campaign` carries `is_holdout = false` on every organic row by design, because an organic/SEO program cannot be switched off for a chosen cell. Reported as `incrementality_measurable = False` with the reason attached, never imputed from a measured channel.
3. **The choice of attribution model matters roughly an order of magnitude less than the correlational-vs-causal distinction.** Swapping first-touch for last-touch moves paid's share by 0.49pp; the causal correction removes 35.2% of paid's credit. A team arguing about which MTA model to adopt is arguing about the smaller of the two effects in this data.

**Community's channel-level estimate is not individually significant** (z = 1.95, resting on a single control conversion) and is stated as such; only the pooled figure clears the significance bar. Per-cell z runs 1.36–2.35 — individual cells are underpowered by design, since the holdout carries only 10% of its channel's budget.

### Targets and floors — PROPOSED, not yet confirmed

No accuracy/error target applies (structural/descriptive). Six floors stand in its place. Two are hard invariants; four are this artifact's own proposals at build time, carrying the same PROPOSED status as the variance engine's ±8% threshold, the segment-migration analysis's 10% firmographic-rescore floor and capacity planning's 15% achievability margin. Nothing upstream (build spec, QA plan, metric tree) states a number for any of the four.

1. **Credit conservation ≤ 1e-9 / $0.01, and first-touch/lead-source agreement exactly 100%.** Hard structural invariants, not really "proposed" — deterministic arithmetic has no sampling variance, and a tolerance would imply an error source that does not exist. The same reasoning capacity planning gives for stating its tie-outs as exact.
2. **Pipeline-generated identity ≤ 1e-9.** Same category.
3. **Mix-shift floor: first-vs-last TVD ≥ 0.005.** Grounded in the noise of the quantity it measures. Under a null of symmetric channel switching, the net flow per channel has a standard error of about `sqrt(n_switchers) / n_converting` ≈ `sqrt(119)/2,061` ≈ **0.53pp**, so 0.5pp is roughly the smallest shift distinguishable from switching noise at all. Observed 1.55pp sits ~3× above it.
4. **Channel-switch floor: ≥ 2% of converting leads.** The mechanism that makes any mix shift possible. `generators/config.py` routes `CROSS_CAMPAIGN_TOUCH_RATE` (0.22) × `CROSS_CHANNEL_TOUCH_SHARE` (0.30) = **6.6%** of follow-up touches across sub-channels, and the observed 5.77% is consistent with that. A 2% floor is unambiguously non-trivial while leaving ~3× headroom — the same reasoning shape as the segment-migration analysis's 10% floor.
5. **Incrementality reconciliation: pooled measured share within ±0.20 of the designed 0.65, pooled z ≥ 2.58, and control below treated in every fully-resolved cell.** The designed figure is `generators/config.py`'s `HOLDOUT_CONVERSION_SUPPRESSION = 0.35` — a suppressed cell is built to convert at 35% of its channel's treated rate, i.e. a designed incremental share of 1 − 0.35 = 0.65 — cited as *grounding*, never as an input. ±0.20 is grounded in the precision the control arm actually supports: the pooled estimate rests on **10–14 control conversions** across the two checkpoints, whose delta-method standard error is **0.088 (2025-12-31) / 0.103 (2025-06-30)**, so ±0.20 is ~2.0–2.3 SE. Tighter would trip on ordinary sampling variation in a deliberately small control group; looser would stop catching a genuine collapse of the suppression mechanism. Observed 0.6819 and 0.6847 at the two checkpoints, both ~0.4 SE from the designed value.
6. **Spend level agreement: ≤ 15%, over a window of ≥ 12 months.** Deliberately *not* the build spec's 0.3% figure, and the distinction is the honest part. The spec's 0.3% is a **complete-window** property and it holds (0.331% over `fact_marketing_spend`'s full 36-month extent). It does **not** hold at a truncated `as_of_date`: the two spend surfaces are generated independently at different grains and calibrated only in aggregate, so month-level divergence runs up to ~2× and cumulative divergence across quarterly `as_of` dates from 2023-06 onward runs **0.9%–10.1%** (30.2% at a 3-month window, which is why the 12-month minimum exists; **0.3%–6.1%** across the nine `as_of` dates that clear it). Asserting the spec figure as an as-of-date check would fail this artifact for a property the data never claimed. 15% is matched to what the check is *for* — licensing campaign budget to be read as spend, which needs level agreement, not penny agreement — at ~2.5× the worst observed ≥12-month divergence and still an order of magnitude tighter than the factor-of-2 error that would genuinely invalidate the reading. Both figures are reported separately (`pct_diff` and `meets_spec_full_window_claim`).

**Drift review trigger**: per the doc's general rule, 2 consecutive monthly checkpoints failing any of the six → flagged for review. In practice the three exact invariants are expected never to breach (a breach is a defect to fix, not a trend to watch). Three are genuinely worth watching in `fact_model_performance_history`. **`first_to_last_mix_shift_tvd`** and **`channel_switch_share`**: if either collapses toward its floor, the multi-touch apparatus has stopped distinguishing anything and the artifact's central diagnostic is empty. **`measured_incremental_share_pooled`**: drifting outside 0.45–0.85 means the holdout cells have stopped functioning as a control and the causal arm needs re-grounding rather than re-running. All three are natural `drift-monitor` hooks.

**Sample sizes** (2025-12-31): 47,118 leads created to date — 2,061 converted, 38,571 lapsed, 6,486 open; 135,965 touches across 182 campaigns; 2,061 × 4 models of attributed credit totalling $20,721,252 in won new-logo bookings; 6 holdout cells (5 fully resolved) covering 4,751 treated and 1,168 control resolved leads.

**Persistence**: scalar time-series metrics logged to `fact_model_performance_history` via `analytics/model_performance.py`'s `log_performance()` — `structural_checks_total`/`_passed`, `converting_leads_attributed`, `attributed_bookings_usd`, `credit_conservation_max_abs_diff`, `bookings_conservation_max_abs_diff_usd`, `first_touch_lead_source_match_rate`, `pipeline_generated_identity_max_abs_diff`, `campaign_vs_coarse_spend_pct_diff`, `first_to_last_mix_shift_tvd`, `channel_switch_share`, `multi_channel_path_share`, `time_decay_half_life_days`, `measured_incremental_share_pooled`/`_pooled_se`/`_paid`/`_community`, `incrementality_pooled_z_stat`, and `{first_touch,last_touch,linear,time_decay}_share_{organic,paid,community}` — 30 metrics per checkpoint. The variable-width tables (the full channel-mix panel, the Layer-3 diagnostics, the per-cell incrementality breakdown, the switching matrix) do not fit that log's flat scalar grain, per `analytics-engineering-conventions`' Persistence note, and are the structured detail recorded in this entry instead.

### Known limitations

- **The mix shift's direction is a property of the generator's routing rule, not of funnel position.** Cross-channel touches are routed uniformly among the non-sourcing sub-channels, so the smallest channel structurally gains under last-touch. The shift is real and the models genuinely disagree — that part is validated — but this data cannot demonstrate the top-vs-bottom-of-funnel ordering the textbook expects, and no claim to the contrary is made anywhere in the module. A generator change (routing cross-channel touches by funnel position rather than uniformly) would be the honest fix, and is a Phase 1 change, not a Phase 4 one.
- **Attributed "pipeline" is won bookings.** Lost new-business opportunities carry no `account_id`, so lost pipeline cannot be traced to a lead and a literal pipeline-dollar attribution is not computable. ROAS is reported as a bookings ROAS throughout, named for what it is.
- **Organic has no causal read and cannot get one from this data.** It is the largest attributed channel and the only one with no suppressed cell. This is a deliberate design property (`dim_campaign`'s own header: an organic/SEO program cannot be switched off for a chosen cell), not a gap to close — but it means the causal arm covers roughly half of attributed credit at most.
- **Per-cell incrementality is underpowered by design.** The holdout carries 10% of its channel's budget (`HOLDOUT_BUDGET_SHARE = 0.10`), so individual cells run z = 1.36–2.35 and community's channel-level pooled estimate rests on one control conversion. Only the all-cell pooled figure clears the significance bar, and only it is used for the validation check.
- **Community 2025Q1 is censored until 2026-02** and will stay out of the pooled estimate until then. That is the resolution horizon working as intended, not missing data.
- **No mart exposes the credit panel or the touch sequence.** Every consumer currently has to re-derive them through this module — including the `cac_by_channel` enhancement above, which is the first concrete second consumer. `mart_marketing_attribution` is the Phase 2 change worth making before that enhancement lands, the same shape of gap capacity planning records for `mart_rep_capacity`.
- **`lead_scoring_history` is not generated**, so nothing here reads a point-in-time lead score. `fact_leads.lead_score` is a terminal-state composite that leaks the outcome and is deliberately untouched. Lead-quality-weighted attribution becomes possible when that table exists — build spec item #11, Wave 7.

## Forecast (sales bottoms-up / ML / CRO overlay reconciliation)

- **Built**: `analytics/forecast.py`. Grain: one row per (period, segment) forecast lens, where period is a fiscal quarter and segment is Commercial or Enterprise. Reads `fact_forecast_submissions`, `fact_opportunities`, `fact_opportunity_stage_history`, `fact_cro_forecast_adjustments`, `dim_reps` and `mart_account_health` — all marts-layer models in `main_marts`, per `analytics-engineering-conventions`' corrected read-scope rule (the boundary is the finished marts layer, `dim_*`/`fact_*`/`mart_*` under `dbt/models/marts/`, not a `mart_*`-prefix-literal reading). No dbt model was added or changed for this artifact; no Phase 1 generator was touched.
- **What it is**: build spec item #2, the second Wave 2 artifact. Three lenses on one question — how much will close this period — reconciled against each other rather than collapsed into one number. The places they disagree are the artifact's actual output, the same way the rep-vs-manager gap inside `fact_forecast_submissions` is a signal rather than noise to average away.
- **Scope — Commercial/Enterprise only, by construction not by filter**: build spec Section 1 gives SMB a no-touch motion closing in 0–7 days with no rep, no stage history and no weekly forecast cadence, and `fact_forecast_submissions` carries no SMB row for that reason. SMB is not forecast here and is not silently folded into a blended company number.

### Shape decision — hybrid, and explicitly not one type

This artifact is deliberately two of `analytics-engineering-conventions`' three categories bolted together. Stating that is more honest than forcing one validation style onto all of it:

| Component | Shape | Validation package |
|---|---|---|
| 1. Bottoms-up roll-up (rep lens and manager lens) | Structural/logic. One quantity is estimated (the category probability weight); the roll-up itself is an exact weighted sum | Structural tie-out + a grounding check on the estimated weights + an out-of-sample dollar reconciliation. **No coefficient table, no AUC, no confusion matrix, no R²** |
| 2. ML lens | Genuine classification model | The full "Classification models" package: model-choice rationale, full coefficient table, held-out AUC, confusion matrix at the real operating threshold, calibration note, sample sizes |
| 3. CRO overlay | Structural lookup | An anti-fabrication check (below). No statistics apply |
| 4. Reconciliation | Structural/logic | A non-vacuousness/non-triviality check on the divergence flag |

**There is no regression model anywhere in this artifact, and that differs from `analytics-engineering-conventions`' expectation that "forecast" would be one.** That line was written before the data was examined — the same caveat the Capacity planning entry records for itself. Against the data that actually exists: the quantity being forecast is a sum of per-deal dollar amounts the CRM already states, and what is genuinely unknown is which of those deals closes won. That is a binary outcome per deal, so the honest model class is a win-probability classifier and the dollar forecast is its expectation under the CRM's own stated amounts. Regressing a period total directly would fit ~12 quarterly observations per segment, discard every deal-level driver, and produce an estimate no one could decompose or act on. **So no R²/RMSE or residual-diagnostics section appears below, and its absence is deliberate rather than pending.**

### Point-in-time design

Every function takes `as_of_date`. Submissions filter to `snapshot_date <= as_of_date`, opportunities to `created_date <= as_of_date`, stage history to `entered_date <= as_of_date`, CRO adjustments to `timestamp <= as_of_date` (an override filed later in the quarter is not knowable at an earlier call), and account usage to the last month that had already **ended** at the evaluation date (a call on 14 Nov reads October's Actions, never November's). Closed-outcome fields — `is_won`, `loss_reason`, the deal-grain `forecast_category` — are never model inputs.

**`close_date` is used for exactly one thing — deciding which quarter a deal belongs to — and never as a feature.** Stated rather than left implicit, because it is the one hindsight-adjacent field this module touches. Phase 1 generates no separate "expected close date" CRM field, so `close_date` stands in for it; `generators/forecast.py` records that cycle length "is drawn from the same distribution for won and lost deals upstream, so the length of the series carries no outcome information either," and the generator's own CRO-adjustment code scopes its quarter the same way. A deal's `close_date` says *when* it resolved, not *how*.

**Seeding**: `_RANDOM_SEED = 42` covers the one stochastic step (the seeded-random draw of which forecast call each closed deal is evaluated at) and the two `train_test_split` calls.

### Component 1 — bottoms-up roll-up (structural)

Each open deal's `amount` is multiplied by the probability weight of whichever category the chosen lens carried at the most recent call on or before `as_of_date`, and the products are summed per segment. Two separate numbers are produced — a **rep-lens** roll-up and a **manager-lens** roll-up — rather than one blended figure, since they genuinely diverge and collapsing them discards the signal the snapshot table exists to carry.

**The probability-weight mapping is derived from realised close rates, not asserted.** Three deliberate properties:

1. **Dollar-weighted, not count-weighted.** For `Σ(amount × w)` to reproduce realised won dollars, `w` has to be the share of *dollars* that convert, not the share of deals.
2. **Keyed by (segment, opportunity_type), never pooled.** Load-bearing, not tidiness: pooled and dollar-weighted (matching property 1's own weighting, not a separate count-weighted read), `Commit` carries an **84.05%** close rate in this data — but **49.90%** of pooled Commit dollars sit on expansion deals that close won by construction. Within new business the same category closes at **43.70%**. A pooled mapping would price a Commercial new-business Commit deal at roughly **3.02×** its real conversion.
3. **Shrunk, then isotonically ordered.** Cells are shrunk toward their `(segment, opportunity_type)` base close rate by `_WEIGHT_SHRINKAGE_PSEUDOCOUNT = 40` (adopted from `generators/forecast.py`'s own `_TRAILING_SHRINKAGE_PSEUDOCOUNT`, not newly invented), so a thin cell falls back to its parent and an empty cell lands exactly on it. The result is then passed through a weighted pool-adjacent-violators step across category rank. **That second step fixed a real defect found at build time**: the four categories are ordinal by definition, but shrinkage toward a high parent rate inverted the ordering for both renewal cells — Commercial renewal priced `Omitted` at 0.659 against `Pipeline` at 0.485, and Enterprise renewal (which has *no* Omitted observations at all) priced it at the 0.848 parent rate against `Pipeline` at 0.706. A mapping that prices a written-off deal above a Pipeline deal is wrong on its face regardless of what a thin sample showed. Pooling adjacent violators weighted by evidence collapses exactly those indistinguishable cells into one shared weight instead of inventing an ordering the sample cannot support.

### Component 2 — the ML lens (fitted classifier)

**Model choice and why — logistic regression, `sklearn`, `random_state=42`, and deliberately WITHOUT `class_weight='balanced'`.** Four reasons, all tied to this artifact's own constraints rather than inherited from the Account health score entry:

1. **Calibration is the requirement here, which is the opposite of the health score's situation.** The health score uses `class_weight='balanced'` and documents, correctly, that this breaks calibration — acceptable there because its output is consumed as a *ranking* (quantile risk tiers). This lens's output is multiplied by dollars and summed, so a systematically inflated probability becomes a systematically inflated forecast, one for one. Balancing is therefore not applied, and the ~40% won rate in this population is mild enough that nothing is given up for it. Gradient boosting was the credible alternative and was rejected partly on the same ground: it is poorly calibrated out of the box and would need a separate isotonic/Platt calibration step layered on, adding a second fitted object between the model and the dollar figure.
2. **Every coefficient is directly attributable to one input**, which is what makes the coefficient table below possible without SHAP or permutation importance standing between the model and its own explanation. A forecast a CRO is expected to override has to be auditable, not merely accurate.
3. **Dataset scale.** 1,881 training-eligible closed opportunities and 23 model inputs after encoding. A higher-capacity model risks fitting noise without a proportionally richer dataset to justify it — and it is not needed: the target below is met with the linear model.
4. **Alternatives considered and rejected by shape, not by default.** A *survival / time-to-event* model was rejected because the question asked is binary at a fixed horizon ("does this deal close won by period end"), not a hazard over time. A *stage-weighted historical-rate lookup* was rejected as redundant — the bottoms-up lens already is a lookup of exactly that kind, so building a second one would give the reconciliation two copies of one opinion.

**Why the ML lens does not read the forecast categories — the single most important design decision in this artifact.** The most predictive observable at any call is the manager's own category, and it is deliberately excluded from the feature set. The bottoms-up lens *is* the forecast categories, priced at their observed close rates. An ML lens built on top of the same categories would be a refinement of lens 1 rather than an independent third read, and component 4 would be measuring rounding rather than genuine disagreement. The classifier therefore reads only **deal mechanics**, which makes "the ML lens disagrees with the manager roll-up" a statement about deal mechanics contradicting human judgement — the diagnostic this artifact exists to surface. The rep-vs-manager gap's own predictive value is reported as a *measured* diagnostic (below) rather than folded into a model.

**Features (11 numeric + 3 categorical, 22 columns after encoding):** `account_usage_trend_ratio` (the account's last complete month of Actions ÷ the mean of the three before it), `has_entered_a_stage`, `stage_progress`, `days_in_current_stage`, `stage_stall_ratio` (days in stage ÷ the segment/type's expected days per stage), `deal_age_days`, `deal_age_ratio`, `poc_revealed_pass`, `poc_revealed_fail`, `rep_is_ramping`, `rep_tenure_days`; categorical `segment`, `opportunity_type`, `current_stage`.

**A twelfth numeric feature, `days_to_period_end` (days from the evaluation date to the end of its quarter), was built, fitted, and then removed as a genuine point-in-time defect, not a tuning choice.** `analytics-model-validator` caught it: in training every row carries its own evaluation date, so the feature varies and picks up real-looking signal — but that signal is deal-close-date position within the quarter (won deals close earlier in their quarter than lost ones on average in this data), which is a post-close attribute leaking backward, not a pre-close-knowable one. Worse, at scoring time every open deal is evaluated at one shared `as_of_date`, so the feature is a **constant** across the entire scored population — it contributes zero discrimination where it is actually used, while still applying whatever log-odds coefficient training assigned it as a fixed offset to every production prediction. Removing it moved the canonical checkpoint's held-out AUC only slightly (0.8098 → 0.8153) and, more tellingly, cut the ML lens's aggregate backtest under-forecast bias from **−12.13% to −5.29%** — direct evidence the leaked feature was injecting a real, constant downward bias into every production-time forecast, not just an in-sample fitting artifact that a held-out AUC alone would have surfaced. All figures below are post-removal.

Three feature decisions worth stating rather than leaving implicit:

- **POC outcome is gated on the POC having actually concluded.** `fact_opportunities.poc_outcome` sits at deal grain with no reveal date. `generators/forecast.py` gates its own use of it on the deal having moved past the POC stage or having sat in it at least 14 days; the identical gate is applied here. Reading `poc_outcome` ungated would hand the model a result for a deal that has not reached POC yet — a leak, not a feature.
- **"Created but not yet staged" is its own encoding, not an imputation.** A deal sits created-but-unstaged for a median 7–17 days in this data (its first stage row is entered after creation). That is a real point-in-time state, so it gets `stage_progress = 0.0` and a `pre_stage` category rather than a median fill that would silently place an unstaged deal mid-funnel.
- **`discount_rate`, `list_price` and `amount` are excluded as features, and the knowability question was checked explicitly rather than assumed.** Two independent reasons, either sufficient. (1) *Knowability*: `generators/forecast.py` states that `amount` is the final negotiated figure, set together with `discount_rate` at generation time — from the account's committed volume for a won deal and from a separate draw for a lost one — so "none of the three can be treated as a stable pre-close observation." (2) *Empirically there is nothing to lose*: on the fitted training population specifically (closed Commercial/Enterprise new_business and renewal, the population this section describes), mean `discount_rate` for Commercial new business is **0.1246 (lost) vs 0.1214 (won)**, a 0.3pp gap, and for Enterprise new business **0.2034 vs 0.2041**, a gap of essentially zero and in the wrong direction to help. The gap stays negligible (≤0.35pp) on every closed-deal population checked, not just this one. Including it would mean taking a field the generator says isn't observable pre-close in exchange for no measurable signal. `amount` does separate (Commercial new business: lost $26.1K vs won $22.7K mean), which is precisely why it is kept out of the *classifier* — it is used only to dollar-weight the roll-ups, the one use `generators/forecast.py` explicitly allows ("a coverage ratio is by definition computed on CRM-stated deal sizes").

**Training population and label design.** One row per **closed** Commercial/Enterprise `new_business`/`renewal` opportunity with `close_date <= as_of_date`, evaluated at one seeded-random forecast call drawn from the calls filed on it inside its own closing quarter. One row per opportunity, not one per call: a deal open for eleven weeks files eleven highly-correlated snapshots, and counting them as independent would inflate the sample and let near-duplicate rows straddle a train/test boundary. Drawing the call at random from inside the closing quarter, rather than fixing a lead time, is what makes training comparable to production — and the comparability is measured, not assumed: **training lead time to close is mean 16.6 days / median 13 (n=1,881), the production scoring population at 2025-11-14 is mean 17.1 / median 17 (n=146).**

**Expansion is excluded from the fitted population, and that is a finding rather than a convenience.** Every one of the 918 closed expansion opportunities as of 2025-11-14 closed won ($14.6M Commercial across 835 deals, $22.5M Enterprise across 83), because `generators/opportunities.py` opens an expansion opportunity only once the account's own usage has already crossed the commitment it formalises. A classifier fitted on a perfectly separable class learns the class indicator and nothing else. Expansion dollars are instead priced at their **observed** historical close rate as of `as_of_date` (1.000, computed not asserted) and tagged `probability_source = observed_close_rate`, with the count reported per segment as `deals_priced_structurally` (51 Commercial / 12 Enterprise at 2025-11-14). This is the one structural, non-fitted component inside the ML lens and it is labelled as such in the output.

**Split — out-of-time, not random.** Rows sorted by evaluation date, last 25% held out, so every holdout row post-dates every training row. This model's production use is "fit on closed history, score the quarter now in flight", and a random split would let it train on deals from the same quarter it is scored on. The stratified random split `analytics/health_score.py` uses is still computed and reported alongside for methodological comparability — secondary, not the headline. The backtest (component 4) provides a second, dollar-level out-of-time read across 24 period-segments.

#### Target — stated before fitting, three criteria

Recorded here per `analytics-engineering-conventions`' rule that an artifact with no stated success criterion cannot be validated later. The health score's 0.65–0.80 band is **not** copied over; the reasoning is re-derived for this problem and lands somewhere else.

1. **Pooled out-of-time held-out AUC: 0.70–0.85.** *Floor above the health score's* for two reasons: the scoring horizon is at most one quarter (median 13–17 days to close) against the health score's deliberate 5-month early-warning lead, and the pooled population mixes `new_business` (~28% base close rate) with `renewal` (~86%), so `opportunity_type` alone separates a large part of it. That second reason is also exactly why a pooled figure cannot be the whole target — hence criterion 2. *Ceiling* because the generator holds back a per-opportunity latent effect constant across an opportunity's snapshots and injects genuine rep/manager noise, and outcomes are assigned upstream on drivers the propensity only partially tracks. A pooled AUC above 0.85 should be read as an alarm that the model found something a forecaster could not have known — the same inflated-AUC failure mode the Account health score entry's calibration note documents and guards against. **It is a leakage alarm, not a performance cap**, and a breach is investigated rather than celebrated (see the 2025-08-15 checkpoint below).
2. **Within-stratum criterion, stated as a ratio rather than an absolute AUC: in every `(segment, opportunity_type)` stratum with ≥ 100 held-out deals, model AUC ≥ 0.95 × the manager-category-lookup AUC on the same held-out rows.** Grounding: each stratum has a genuinely different achievable ceiling — the manager's own category separates Commercial new business by only ~9 points of close rate end to end in this data (0.183 → 0.278) while it separates Commercial renewals by ~44 (0.514 → 0.953) — so a single absolute floor across strata would be importing a number from another artifact's context rather than deriving one from this one's. The manager lookup on the same rows *is* that stratum's demonstrated ceiling, and it is leak-proof by construction (a human judgement filed before the close, priced at its own historical rate). The criterion therefore asks the genuinely interesting question: can a model built on **disjoint inputs** recover essentially all the discrimination the human call demonstrates?
3. **Held-out calibration gap: |mean predicted probability − actual base rate| ≤ 0.05.** Load-bearing here in a way it is not for the health score, because the lens is summed as `Σ(amount × p)` into a dollar figure. 0.05 on a ~0.40–0.48 base rate is a ≤ 12.5% relative dollar bias — deliberately set inside the divergence threshold below, so mis-calibration alone cannot be what makes the ML lens diverge from the others.

**Second checkpoint, `as_of_date` 2025-08-15 (mid-2025-Q3): the AUC ceiling was breached, and it is reported as a breach rather than absorbed — and, on independent review, its cause is genuinely unexplained, not composition as an earlier draft of this entry claimed.** Out-of-time held-out AUC **0.8593** (post the `days_to_period_end` removal above — the leak was checked as a candidate explanation for this breach and ruled out below) against the stated 0.70–0.85 band; calibration gap +0.0150 and both gated within-stratum ratios met (Commercial new_business 1.101×, Commercial renewal 1.176×), so `check_ml_targets` fails on the ceiling alone and the checkpoint records **5 of 6** checks passed.

The manager-category-lookup baseline — leak-proof by construction, since it reads only the manager's own category, an input disjoint from the classifier's feature set — scores **0.8357** on the same held-out rows, so the model sits **1.028×** that reference; the equivalent ratio at the canonical checkpoint is **1.043×**. `analytics-model-validator` corrected the reasoning an earlier draft built on these two ratios: "the ratios are nearly identical while the absolute AUCs differ ⇒ this must be composition, not leakage" is a non-sequitur, because the lookup baseline is constructed from inputs the classifier's features never touch — a leak living *inside those features* cannot move the baseline at all, so a persistent leak present at both checkpoints would produce exactly this same "identical ratio, different absolute AUC" signature and pass unnoticed. The ratio check is real evidence against **feature leakage specifically appearing at one checkpoint and not the other**; it says nothing about a leak present throughout, and does not by itself support a composition story.

The composition story was checked directly and does not hold either: the holdout's renewal share is **0.3546** at 2025-08-15 vs. **0.3544** at 2025-11-14 — essentially identical, not higher. A composition-standardized comparison (applying the canonical checkpoint's own stratum mix to both) puts within-stratum discrimination at **0.6765 at 2025-11-14 vs. 0.7331 at 2025-08-15** — every stratum is more discriminable at the breaching checkpoint, Commercial new_business alone moving from 0.5249 to 0.6131 pre-fix (comparable movement holds post-fix). Roughly all of the raw 5.15-point gap between the two checkpoints is within-stratum, not mix. **The breach is real, is not explained by the leak candidate this fix removed, and is not explained by holdout composition either — it is recorded as an open, unexplained breach**, which is the honest state of a leakage alarm that has fired without a diagnosed cause, not a reason to loosen the alarm.

**On the proposed ratio-based ceiling (≤1.15× the leak-proof baseline, replacing the absolute 0.70–0.85 band): rejected, on `analytics-model-validator`'s recommendation.** The observed ratios at both checkpoints (1.043×, 1.028×) sit far below 1.15× — a ratio-based ceiling **would not have fired at either checkpoint**, including the one with an unexplained 5-point within-stratum jump the absolute band correctly caught. A ceiling that misses the only anomaly on record is not a working alarm, and per the paragraph above the ratio is structurally blind to a leak that inflates both the model and the (feature-disjoint) baseline together. The absolute band stays the operative target. The composition-standardized within-stratum AUC computed above is retained as a **second, logged diagnostic** — it answers "was this an easy holdout slice" directly, which is the question the ratio was actually trying and failing to answer.

### Component 3 — CRO overlay (structural lookup, never fabricated)

A logged override is applied verbatim as a dollar delta on top of the roll-up. **Where no row exists for a `(period, segment)`, the adjustment is exactly 0.0, `has_logged_cro_adjustment` is False, and the adjusted figure equals the unadjusted one to the bit.** Nothing is interpolated, smoothed, carried forward from a neighbouring quarter, scaled, or inferred from the reasons present elsewhere in the log. `fact_cro_forecast_adjustments`' own grain comment says an absent `(period, segment)` pair means "no override filed", never "missing data", and a fabricated adjustment would be this artifact inventing a leadership judgement that was never made. The log holds **18 rows across 11 distinct quarters × 2 segments** (2024-Q3 carries no logged row for either segment); at the canonical checkpoint **6 of the 24 backtested period-segments have no logged override and all 6 carry a zero adjustment**.

**The overlay is applied to the manager bottoms-up roll-up, not to the rep roll-up or the ML lens — that is its provenance, not a preference.** `generators/forecast.py` derives each logged override from the manager-categorised roll-up at the quarter's first call (against a pipeline-coverage, rep-sandbagging or late-stage-slippage read), so the manager lens is the number the override was actually filed against. The same delta applied to the ML lens is reported alongside as `cro_adjusted_ml_forecast`, clearly secondary.

### Component 4 — reconciliation, and the divergence flag

`reconcile_period()` returns one row per `(period, segment)` carrying all four lenses side by side — `bottoms_up_rep`, `bottoms_up_manager`, `ml`, `cro_adjusted` — plus `lens_spread_pct` = (max − min) ÷ mean, `lenses_computable` (3 rather than 4 in the early quarters, before enough closed history exists to fit the classifier — reported, not hidden), `widest_pair` naming which two lenses are furthest apart, and `diverges_materially`.

`backtest_reconciliation()` runs the same machinery at **every** quarter's mid-quarter forecast call (the last Friday on or before the quarter's midpoint — a fixed relative position, so every quarter is evaluated at a comparable point in its own cycle). Each quarter is evaluated using only data available at *its own* call: weights re-derived and the classifier re-fitted from deals closed as of that date. A single model fitted at `as_of_date` and applied backwards would leak every later quarter's outcomes into every earlier quarter's forecast — the exact failure the point-in-time rule exists to prevent. For quarters that have since completed, `realised_won_amount` is the actual closed-won dollars of **exactly the population the lenses forecast** (same deals, same scoping), so lens error is measured against a like-for-like denominator rather than a period total including deals no lens ever saw.

**Divergence threshold: spread > 25% of the lens mean — PROPOSED, not yet confirmed, and its grounding is restated below following `analytics-model-validator`'s review.** Nothing upstream (build spec, QA plan, metric tree, design brief) states a number for this, so it is this artifact's own proposal at build time, carrying the same PROPOSED status as the variance engine's ±8% threshold, the segment-migration analysis's 10% firmographic-rescore floor and capacity planning's 15% achievability margin.

| Lens | MAPE per period-segment | Aggregate dollar bias |
|---|---|---|
| Bottoms-up, rep | 15.46% | +0.20% |

Two things worth stating plainly. The **rep lens is not worse than the manager lens on these measures**, despite the rep call carrying a designed optimism bias — because the bottoms-up weights are estimated *per lens*, so a systematically optimistic category is simply priced at a systematically lower weight. The bias lives in the categories; the weighting removes it. And the **ML lens still carries a −5.3% aggregate under-forecast across the backtest despite being well calibrated at every individual fit** — down from an original −12.1% before the `days_to_period_end` feature was removed, which is itself evidence that feature was injecting a real production-time bias rather than only an in-sample artifact. The residual −5.3% has the same underlying cause the −12.1% did: each backtest quarter re-fits on history only, and the population's base close rate rises steadily over the window as the renewal mix grows, so a model fit on older history systematically under-predicts a newer quarter. That is genuine out-of-time calibration drift from mix shift, not a defect to patch, and it is the strongest argument in this artifact for keeping four lenses rather than picking one.

### Rep-vs-manager gap — the build spec's claim, measured not modelled

Build spec Section 4 asserts that "opportunities where the manager downgrades a confident rep call close at a measurably lower rate than opportunities where the two agree." `measure_rep_manager_gap_signal()` checks it directly on closed deals as of `as_of_date`, over calls filed inside each deal's closing quarter: among **7,487** confident rep calls (Commit or Best Case), the **1,467** the manager downgraded closed at **56.3%** against **76.5%** for the **5,965** where the two agreed — a **20.2pp downgrade penalty** (20.0pp at the 2025-08-15 checkpoint, i.e. stable). The signal is real and is reported; it is deliberately **not** given to the classifier, per the lens-independence decision above.

### Target and drift threshold

- **Target**: the three ML criteria stated above (pooled out-of-time AUC 0.70–0.85, within-stratum ≥ 0.95× the manager-lookup ceiling on strata with ≥ 100 held-out deals, calibration gap ≤ ±0.05). The structural components have no accuracy target — the six checks above stand in its place, and the three exact tie-outs (`rollup_ties_to_deal_detail`, `cro_overlay_never_fabricates`, the monotonicity/pass-through half of `weight_mapping_is_grounded`) are stated as **hard invariants with a floating-point tolerance rather than a band**, on the same reasoning the Weekly executive readout and Capacity planning entries give: deterministic arithmetic has no sampling variance, and a tolerance would imply an error source that does not exist.
- **Drift threshold**: per this doc's general rule, **2 consecutive monthly checkpoints** breaching → flagged for review. Concretely: `ml_auc_holdout_out_of_time` outside **0.70–0.85**; `ml_calibration_gap` outside **±0.05**; `ml_auc_ratio_vs_leak_proof_baseline` above **1.15** (the leak alarm proper, independent of holdout composition); `divergence_share_flagged_backtest` reaching **0.00 or 1.00** (a flag that has gone vacuous or trivial); any of the three exact structural tie-outs failing — the last being a defect to fix rather than a trend to watch. The two genuinely worth watching in `fact_model_performance_history` are `ml_calibration_gap` and `ml_auc_ratio_vs_leak_proof_baseline`: the first is what the dollar figure depends on directly, the second is what tells a future reader whether an AUC movement is the model or the window.
- **Persistence**: scalar time-series metrics are logged to `fact_model_performance_history` via `analytics/model_performance.py`'s `log_performance()` under `model_name = 'forecast'` — `ml_auc_holdout_out_of_time`, `ml_auc_holdout_random_split`, `ml_auc_manager_category_lookup_baseline`, `ml_auc_ratio_vs_leak_proof_baseline`, `ml_precision_commit_grade` / `_recall_` / `_f1_`, the four confusion-matrix cells, `ml_operating_threshold_probability`, `ml_mean_predicted_probability`, `ml_actual_base_rate`, `ml_calibration_gap`, `ml_n_train`, `ml_n_holdout`, `structural_checks_total` / `_passed`, `divergence_threshold`, `divergence_share_flagged_backtest`, `backtest_period_segments`, `backtest_mape_*` per lens, `rep_manager_downgrade_penalty`, and the current period's four lens values plus spread per segment. The variable-width tables (the 24-row weight mapping, the coefficient table, the reliability buckets, the within-stratum AUC table, the full backtest) do not fit that log's flat scalar grain, per `analytics-engineering-conventions`' Persistence note, and are the structured detail recorded in this entry instead.

### Known limitations

- **The ML lens's out-of-time under-forecast is not corrected.** The −5.3% aggregate backtest bias (down from −12.1% before the `days_to_period_end` fix) is a real mix-shift effect (see above) and is reported rather than patched with a recency weight or a bias-correction term, either of which would be a tuned constant with no grounding in an upstream doc. The reconciliation is the honest response: when one lens drifts, the other three are still there and the spread says so.
- **The within-stratum ratio criterion is floor-only, and that is a real gap, not just an asymmetry of convenience.** It asks whether the model recovers *at least* 0.95× the manager-lookup ceiling; it has no upper bound, so it cannot catch a stratum running suspiciously *above* that human ceiling — which is precisely the leak signature the pooled AUC ceiling exists to catch at the pooled level. At the 2025-08-15 checkpoint, Commercial new_business ran 1.101× and Commercial renewal 1.176×, both comfortably passing the floor-only test while sitting on the same unexplained-breach checkpoint discussed above. `analytics-model-validator` recommended adding an upper bound to this criterion (the natural home for a per-stratum leak alarm, unlike the pooled ratio ceiling this entry already rejected); that is not yet implemented and is flagged here as real follow-up work rather than a closed question.
- **Enterprise renewal is too thin to price or model independently** — 32 fitted opportunities, 7 in the held-out split, and no `Omitted` observation at all. Its weight mapping leans almost entirely on shrinkage and isotonic pooling (three of its four categories collapse to one shared 0.7566 weight), and its within-stratum AUC is not a usable read at n=7. Both facts are visible in the outputs rather than smoothed over.
- **The Commercial new-business categories barely discriminate in this data**, and no model can fix that. The manager's four categories span only 0.183→0.278 in observed close rate, and the ML lens's within-stratum AUC on that population is 0.556. Both lenses are honest about it; a reader should not take a Commercial new-business Commit as meaningfully stronger than a Pipeline deal.
- **End-of-window truncation.** `fact_forecast_submissions` ends 2025-12-26 and the last opportunity closes 2025-12-28, so at any `as_of_date` inside 2025-Q4 every open deal scopes into the current period by construction — there is no pipeline extending past the simulation window. `run_forecast()` returns a `data_window` block flagging this rather than absorbing it silently, the same treatment `analytics/variance_diagnostic.py` gives its own end-of-window artifact. An `as_of_date` of 2025-12-31 has zero open deals and produces no forecast at all.
- **No forward-quarter forecast.** This artifact forecasts the quarter `as_of_date` sits in, from the pipeline that already exists. Forecasting a *future* quarter would need a pipeline-creation model for deals not yet opened, which is a different artifact (and build spec item #19, scenario planning, is the one that simulates rather than predicts).
- **The CRO overlay is applied, never explained.** `reason` is carried through to the output, but this artifact does not attempt to reproduce or validate the coverage-ratio / sandbagging / slippage read behind each logged override. Whether the CRO's judgement was right is answerable from the backtest table's `cro_adjusted` error column; why it was made is not modelled here.

## Variance-diagnostic engine

- **Built**: `analytics/variance_diagnostic.py`. Grain: one evaluation month (the last *complete* month at or before `as_of_date` — a mid-month `as_of_date` would otherwise diff a partial month's actual against a whole month's plan). Reads `mart_gtm_plan` (plan side), `mart_growth_bridge` / `mart_efficiency` / `mart_durability` (actuals side, all segment × month, blended here to company-wide grain), and `mart_account_health` (Layer-2 evidence and the watchlist population). No dbt model was added or changed for this artifact.
- **Shape decision — structural/logic, not predictive**: per `analytics-engineering-conventions`' "Structural/logic artifacts" category, which names this artifact specifically: **there is no coefficient table, no AUC, no confusion matrix, no R²/RMSE and no calibration note here, and their absence is deliberate, not pending.** The engine makes no prediction; it walks a fixed tree and compares already-computed mart values. Its correctness claim is "does it identify the true outlier Layer-2 child among true siblings, respecting each branch's real depth," and the only honest way to check that claim is a hand-constructed case with a known unambiguous answer. That check is the synthetic-scenario suite below, run by `analytics-model-validator`.
- **Model type selection and rationale (why not a statistical attribution model)**: a regression-based variance attribution (decomposing a Layer-1 miss onto its children via fitted coefficients) was considered and rejected. The metric tree is already an exact arithmetic identity at every parent — `CLAUDE.md`'s standing invariant is that every parent is the real mathematical result of its children, and `mart_growth_bridge`'s bridge equation is enforced by `tests/assert_revenue_bridge_reconciles.sql`. Where the relationship between parent and children is a known identity, fitting coefficients to estimate it would replace an exact answer with a noisy one, and would introduce a model that could be wrong about arithmetic that cannot be wrong. A deterministic walk of the declared structure is the correct model class here. This is the same reasoning the Segment migration entry above uses for rejecting a migration-propensity classifier.
- **Determinism / seeding**: no stochastic step exists in this module — no sampling, no simulation, no train/test split — so no random seed applies, matching `analytics/segment_migration.py`'s precedent. The synthetic scenarios' "jitter" is a caller-supplied literal sequence, not a random draw, so every scenario is byte-reproducible. The one indirect exception: the watchlist calls `analytics/health_score.py`, which seeds its own model via that module's `_RANDOM_SEED = 42`. This module does not fit, re-fit or replace that model.
- **Point-in-time design**: every loader filters `month <= as_of_date`. `mart_account_health`'s forward-looking columns (`customer_status`, `is_eventually_churned`) are never used to define a historical population — the usage-dip series defines its population as "has a row in this month" and the tenure-at-churn series uses only churns already observed at the month being evaluated.

### Resolved scope decision — playbook triggers are out of scope for this artifact

Build spec Section 5's Phase 4 prose lists "Playbook triggers: binary threshold rules… with a log of which triggers fired" inside the variance-diagnostic engine's deliverable description. Section 8's build-priority order — the section designated as the sequencing authority ("Not an arbitrary ranking — grouped into waves by genuine dependency") — places "Automated playbook triggers" in **Wave 4**, after Wave 1, with the stated dependency "needs Wave 1's thresholds validated against real data first." That dependency is only coherent if the triggers are built *after* this engine's thresholds exist and have been validated, not alongside them. Resolved in favour of Section 8: **no playbook-trigger logic is built here**, and nothing in this artifact reads or writes `fact_playbook_triggers` (which does not exist in `data/raw/` — it remains unbuilt Phase 1 scope). Playbook triggers stay a Wave 4 artifact with its own methods-doc entry when built.

### Variance mechanisms — three, not one

Each Layer-1 row carries a `mechanism` column naming which applies, rather than blending them into a single number:

| Mechanism | Applies to | What it is |
|---|---|---|
| `plan_diff` | 8 metrics — new_logo_consumption_revenue, expansion_consumption_revenue, contraction_churned_revenue, consumption_payback, onboarding_cs_efficiency, nrr, grr, logo_retention | `(actual − plan) / abs(plan)` for the evaluation month |
| `trailing_baseline` | Activation only | `(actual − mean of prior 3 months) / abs(baseline)` |
| `not_computable` | magic_number, am_efficiency | Plan value reported; actual and variance are `None` |

**Activation's exception** is by design, not a workaround. `mart_gtm_plan` deliberately carries no plan row for Activation (its own header, and `generators/gtm_plan.py`); the design brief's sample readout reports it as "2.1 days vs. 2.4d last month" — a trailing baseline, not a plan figure. The mechanism (trailing baseline) is that precedent; the window length is this artifact's own resolved decision: the mean of the prior **3** months rather than the single prior month, since a one-month comparator is the noisiest possible baseline. The prior month's raw value is reported alongside (`prior_month_value`) so a readout can render the design brief's exact phrasing. **Degenerate in the current data**: blended TTFA is identically 0 in every month of the 36-month window — `fact_usage_monthly` is monthly grain and every account records its first Action in its own signup month (`mart_growth_bridge`'s own Activation comment states this). The mechanism is implemented and exercised, but on this data the baseline is zero and the deviation undefined, so Activation reports `Not computable` rather than a fabricated `On track`. Its Layer-2 child `onboarding_completion_rate` is likewise identically 1.0. A real TTFA signal needs a day-grain first-Action timestamp in Phase 1 plus a mart change — not a Phase 4 workaround.

**magic_number / am_efficiency — variance from plan is structurally not computable.** `mart_efficiency` leaves both NULL on purpose: no rep-cost/comp data exists anywhere in the raw sources, so the denominator of each ratio is undefined (`generators/config.py` records the same gap — "outbound_sdr's channel spend here covers tooling/data enrichment only, NOT rep headcount cost"). `mart_gtm_plan` still carries a plan value for both, which is not a contradiction: a plan is a top-down target and does not need cost data the way a computed ratio does (`generators/gtm_plan.py` assumes `PLAN_AM_FULLY_LOADED_COST_ANNUAL = 180_000` for exactly this reason). The engine reports the plan value, `actual = None`, `variance = None`, `status = "Not computable"`. **An actual is never fabricated to close this gap.** It closes when a comp/cost source exists in Phase 1, not before.

### Blending actuals to `mart_gtm_plan`'s company-wide grain

`mart_gtm_plan` is published blended/company-wide; all three actuals marts are segment × month. Each metric's blend mirrors how `generators/gtm_plan.py` built the corresponding plan anchor rather than being picked ad hoc:

| Metric | Blend |
|---|---|
| new_logo / expansion / contraction+churn | Straight sum across segments. Company-wide segment migration nets to zero by construction (the bridge identity), so the sum is exact. Contraction and churn are summed into one positive magnitude, matching the plan's stored sign convention. |
| Activation (TTFA) | Signup-cohort-size-weighted mean (logo-weighted — TTFA is a per-account average) |
| Consumption payback | Revenue-weighted (`starting_mrr` share) across **Commercial and Enterprise only**, mirroring `gtm_plan._blend(BENCHMARK_CONSUMPTION_PAYBACK_MONTHS, _final_revenue_mix())`, which renormalises over the segments the QA benchmark table covers (SMB is marked n/a) |
| Onboarding/CS efficiency | Aggregate ratio: total AM/CS touchpoints ÷ total automated Actions across all three segments. Matches `gtm_plan._steady_state_touch_per_action()`, which counts SMB's Actions in the denominator with zero touches in the numerator — a real zero, since SMB is no-touch |
| NRR / GRR | Company-wide **monthly** rate is the aggregate dollar ratio (revenue-weighted by construction); the annual-equivalent figure is the **product of the trailing 12 monthly rates**. Compounding, not averaging — a retention rate is multiplicative across periods |
| Logo retention | Identical, on account counts rather than dollars (logo-weighted), mirroring `gtm_plan`'s use of `_final_logo_mix()` for this one metric |
| Win rate / avg initial commitment (Layer 2) | Commercial + Enterprise only. Build spec Section 2: SMB "gets exactly one Opportunity record… immediately Closed Won… SMB has no win-rate concept to true up." Both legs use the same population so the tree's multiplicative identity is not broken by mixing scopes |

**NRR/GRR/logo_retention unit reconciliation**: `mart_gtm_plan`'s values for these three are annual-equivalent decimal rates while `mart_durability` exposes monthly rates — its header explicitly defers this to "a future consumer." Resolved here by compounding the trailing twelve company-wide monthly rates before diffing, as described above. The two sides are never diffed at mismatched units.

### Level-comparability caveats (`plan_comparability` column)

Three Layer-1 metrics are flagged `caveated` — their variance **is** computed, but the levels are not on the same footing and a readout must not present the gap as a business finding:

- **consumption_payback**: the plan anchor is the QA benchmark payback band (Commercial ~14–18mo, Enterprise ~9–13mo), which assumes a fully-loaded CAC. `mart_efficiency`'s actual CAC comes from `fact_marketing_spend` only and systematically excludes sales headcount cost; its denominator is average utilised margin across the whole installed base rather than per *new* account. Both push the computed actual far below the benchmark band — observed plan variance is ≈ −99% in every month, which measures the definitional gap, not performance. The Layer-2 drill-down is unaffected: it ranks each leg against its own trailing baseline, which is immune to a constant level offset.
- **nrr / grr**: the caveat is the **scope of the contraction bucket on the actuals side**, not the plan. `generators/gtm_plan.py` derives its monthly expansion and contraction+churn shares of base *from* the benchmark-blended `nrr`/`grr` anchors — `contraction_share = 1 − grr**(1/12)` (≈ 0.76%/month) and `expansion_share = nrr**(1/12) − 1 + contraction_share` (≈ 1.95%/month), re-derived at each plan year's own rate — so the plan's flow rows and its durability rows are two readings of one identity and reconcile to machine precision. The gap that remains is definitional: over the twelve months to 2025-11 the marts carry gross contraction+churn at ≈ 5.4% of starting revenue per month against gross expansion at ≈ 10.8%, of which outright churn is only ≈ 0.2%. `int_revenue_movements` buckets *any* month-on-month usage decline as contraction, so in a consumption business whose base is planned to grow ≈ 88%/year both gross legs are large and largely offsetting, while a benchmark NRR/GRR band describes durable downsell in a mature base. That single difference drives both signs at once — TTM GRR ≈ 0.51 against a 0.93 plan, TTM NRR ≈ 1.82 against a 1.17 plan. **Logo retention, which has no gross-flow bucket, reconciles to plan within 2%** — the evidence that the churn leg is sound and it is the contraction bucket's *scope* that differs. Closing it means either a durable-vs-transient split in `int_revenue_movements` or a benchmark stated for gross consumption flows; neither is a Phase 4 workaround, and the Layer-2 drill-down is unaffected (it ranks each leg against its own trailing baseline, immune to a level offset).

### Drill-down logic, and the structural guarantee

The most likely failure mode for this artifact is surfacing an intermediate node — Win rate, a Layer-2 child of New logo — and labelling it "Layer 1". That is made impossible structurally rather than by care:

- `_TREE` is the single frozen transcription of `acme-corp-gtm-metric-tree.md`. Every node carries its own `layer` and `parent_key`; `_register()` refuses any node whose layer is not exactly its parent's layer + 1, and a module-level integrity check re-verifies the whole tree at import (11 Layer-1 nodes: 4 Growth / 4 Efficiency / 3 Durability; the branches asserted two-deep vs. three-deep).
- A metric's layer is **never assigned at emit time** — every emitted record reads `layer` off the node definition.
- A scan can only start at `layer1_nodes()` (nodes whose parent is a pillar). There is no code path by which a Layer-2 node enters the scorecard or heads a drill-down.
- `Drilldown.__post_init__` asserts `layer1.layer == 1`, `layer2.layer == 2`, `layer2.parent_key == layer1.key`, and for every leaf `layer == 3` **and** `parent_key == the Layer-2 node's key`. A mislabelled record raises rather than rendering.
- `rank_siblings()` raises on any candidate that is not a registered child of the parent it was asked about, so "the outlier among its siblings" cannot become "the biggest mover anywhere in the tree."
- Layer-3 depth is read from the tree, never assumed, and reported as one of three explicit statuses: `branch_depth_2` (the tree genuinely stops at Layer 2 here — Consumption payback, Onboarding/CS efficiency, Activation, Logo retention, NRR, GRR), `no_computable_layer3` (the tree has a Layer 3 but no mart computes it), `surfaced` (1–2 leaves ranked and returned). **A Layer 3 is never fabricated to force symmetry.**

**Layer-2 ranking key.** Siblings are ranked by deviation from **their own trailing 8-month baseline** — not from the Layer-1 parent's plan, which would just repeat the parent's miss one layer down. Eight periods carries over the design brief's "trailing 8-week average" shape to this engine's monthly grain. Two bases exist, chosen per parent and reported in a `comparison_basis` column:
- `relative_deviation` (default) — % deviation from baseline. Correct wherever siblings carry different units and only a normalised comparison is meaningful. This is the design brief's own read ("24% this week vs. a 31% trailing 8-week average").
- `additive_share` — absolute deviation in the siblings' shared unit. Used for NRR and GRR, whose children are additive components of one identity all expressed as a share of starting revenue. Ranking those by % deviation lets a large relative swing on a near-zero component (churn at 0.1% of revenue) outrank a component that actually moved the parent (contraction at 5%) — i.e. it names the wrong outlier. Validated by the `nrr_additive_share_basis` synthetic scenario.

The tree's two explicitly non-additive nodes — Marketing–sales handoff quality ("a diagnostic overlay on the above three, not a fourth multiplicative factor") and Brand & awareness ("leading indicator, not summed into the pipeline math") — are registered in the tree but never compete in a sibling ranking.

**NRR/GRR grain note**, attached to those drill-downs at runtime: their Layer-1 figure is the trailing-12-month compounded rate (to match the plan's units) while their Layer-2 drivers are read at monthly grain — the grain at which a driver actually moves. A driver can therefore point the opposite way to the annualised parent in a single month; the driver ranking reads as "what moved this month," not as a decomposition of the twelve-month figure.

Two coverage decisions worth stating plainly:

- **`usage_dip_breadth` (Contraction+Churn's one computable Layer-2 child)** — the share of the month's account population whose trailing-3-month mean `actions_consumed` sits below 70% of that account's own cumulative-to-date mean. This operationalises the node's own stated normalisation ("against the account's own historical baseline") from `mart_account_health` alone. It is descriptive — no model is fitted, no probability produced — so it is not a second risk model. Flagged `partial` because it measures the *breadth* of account-relative dips without performing the cyclical-vs-structural classification the node's headline asks for; that needs the node's second leaf (cohort comparison, same account type, same period last cycle), which no mart supports. The 0.70 cut is this artifact's own resolved decision: deep enough to exclude ordinary month-to-month usage noise, shallow enough to catch a fade well before it reaches zero.
- **Account health score is NOT usable as a Layer-2 trailing series.** `analytics/health_score.py`'s `score_accounts()` defines its scored population as accounts whose `customer_status` is `'Active'` — a final-status field. Scored at a historical month, that silently drops every account that has churned since, biasing older months upward and manufacturing a spurious deterioration trend. Rather than publish a biased series, this node is reported as not computable with that reason attached. The health model's **current-state** output is still used, at `as_of_date` only, for the watchlist. Producing an honest historical series needs `score_accounts()` to gate its population on `churn_month > month`, a change to `analytics/health_score.py` outside this artifact's scope.

Because 0 Layer-3 leaves are computable from the marts, every real-data drill-down currently returns either `branch_depth_2` (honest: the branch has no Layer 3) or `no_computable_layer3` (honest: it has one, nothing computes it). The Layer-3 code path is fully exercised by the `new_logo_miss_win_rate_outlier_with_layer3` synthetic scenario.

### Watchlist

Accounts whose composite health score breaches the risk threshold, ranked by ARR at risk (build spec Section 5). Reuses `analytics/health_score.py`'s scored output — `risk_tier == 'High'` and `churn_probability` — directly; **no second risk model is built.** Grain: one row per flagged account.

**ARR caveat, stated rather than buried**: no `mart_*` table exposes ARR at account grain. `fact_revenue_monthly` does, but it is a `fact_*` table outside the mart-only read scope this Phase 4 code operates under. `est_arr_at_risk_usd` is therefore the account's **segment-average** ARR for the evaluation month (`mart_durability` `starting_mrr / starting_accounts × 12`), not its own contracted ARR — a genuinely computed segment figure, named as an estimate. Because this estimate is constant within a segment, sorting by it first degenerates to "order segments by average ARR, then churn probability within segment" — the ranking does what the build spec's "ranked by ARR at risk" literally asks for, but with a real consequence worth naming precisely: **at `as_of_date` 2025-11-30 the top 25 are 100% Commercial.** Enterprise has the highest segment-average ARR (~$470K) but zero accounts in the High risk tier that period (Enterprise churn probabilities sit below the population's 80th percentile), so it never appears; SMB has by far the largest absolute concentration of risk (1,085 High-tier accounts, vs. Commercial's 33) but SMB's much lower segment-average ARR (~$3.3K) means none of it surfaces until `top_n` exceeds Commercial's 33. A reader must not take "Commercial-only" as "SMB and Enterprise are fine" — it reflects this proxy's segment-constant shape and a ranking cutoff, not the real risk distribution. Exposing account-grain ARR in `mart_account_health` (or a new mart) is a Phase 2 change that would make this exact; a stratified or per-segment top-N is a Phase 4-side option that would surface SMB's concentration without waiting on that mart change, and is worth considering before this watchlist is read by anyone who won't have this paragraph in front of them.

### Threshold: ±8% — PROPOSED, not yet confirmed

Adopted from the hand-illustrated sample weekly readout in `acme-corp-claude-design-brief.md`, which used ±8% to decide which Layer-1 nodes earned a drill-down. Build spec Section 7 lists "exact variance threshold for triggering a drill-down (used ±8% in the sample readout — confirm or adjust)" as explicitly still open, so this is carried forward as the documented starting point, not settled — the same treatment the Segment migration entry's 10% firmographic-rescore floor carries. Breach is symmetric (either direction triggers a drill-down), matching what "±8%" says; direction only decides the Ahead/Behind label.

|---|---|---|

| **±8%** | **6.67 of 8** | **83.3%** |
| ±10% | 6.42 of 8 | 80.2% |
| ±15% | 6.00 of 8 | 75.0% |
| ±20% | 5.75 of 8 | 71.9% |
| ±30% | 5.50 of 8 | 68.8% |

At this data's monthly grain, ±8% flags around five sixths of all metric-months — far from the sample readout's 3-of-11 drill-down cadence, and the curve is flat enough that no threshold in this range reaches it: even ±50% still flags half the metric-months. ### Known limitations

- **End-of-window truncation.** The simulation's final month (2025-12) is not a representative evaluation period: every still-active account's last observed month lands in the contraction bucket (contraction+churn spikes to $1.17M against a $300–500K norm), Enterprise marketing spend is absent so blended CAC is incomplete, and Action volume is partial. `run_diagnostic()` returns a `data_window` block that flags this explicitly rather than excluding the month silently; the canonical build-time checkpoint uses `as_of_date = 2025-11-30`. A checkpoint at 2025-12-31 is also logged; both currently show 7 breaching nodes.
- **No Layer-3 evidence is computable from real data today** — all 32 of the tree's Layer-3 leaves depend on sources that are either ungenerated (`content_engagement`, `community_membership`, leads/campaigns, web traffic, rep cost) or exposed only through `fact_*` tables. Closing any of these is a Phase 1 or Phase 2 change.
- **Not subject to drift monitoring.** This artifact has no calibration to drift. `fact_model_performance_history` carries only its structural coverage and correctness scalars (`synthetic_scenarios_passed`/`_total`, `variance_threshold`, `layer1_nodes_*`, `layer2_siblings_*`, `drilldowns_with_genuine_sibling_comparison`) so a future build can be checked against this one. Recurring `drift-monitor` runs apply to the health score, not here.

## Weekly executive readout

- **Built**: `analytics/weekly_readout.py`. Grain: one readout per evaluation period — the last *complete* month at or before `as_of_date`, company-wide/blended, the same evaluation month `analytics/variance_diagnostic.py` defines. Rendered deliverable and structured payload land in `analytics/outputs/weekly_readout_<as_of_date>.md` / `.json` (version-controlled, unlike `data/acme_gtm.duckdb`, so the real-data document is inspectable without rebuilding the pipeline). No dbt model was added or changed for this artifact.
- **What it is**: Wave 1's fifth and final artifact — the build spec's "forcing function that proves the first four work against real generated data." It assembles the already-built artifacts' outputs into the document structure build spec Section 5 specifies (header · executive summary · Layer-1 scorecard · drill-downs · playbook triggers · forecast · watchlist), in the shape of the hand-illustrated sample readout in `acme-corp-claude-design-brief.md`, backed by real data instead of illustration.
- **Inputs — one, deliberately**: `analytics/variance_diagnostic.py`'s `run_diagnostic(as_of_date)` output, in full: `layer1_scorecard` (all 11 Layer-1 nodes), `drilldowns` (one `Drilldown` per breaching node), `watchlist` (which itself consumes `analytics/health_score.py`'s `score_accounts()`), `coverage`, and `data_window`. **This module reads no mart, no `fact_*` table and no database directly** — it holds no DuckDB connection and issues no SQL. Every business figure enters through the artifact that owns it and that has already been validated against its own stated target, so a number in the readout and the same number in its source artifact cannot diverge.
- **It computes nothing, and that is the design**: there is no arithmetic on a metric value anywhere in the module. Formatting a float into `$45.2K`, grouping the eleven nodes into three pillar tables, and selecting which drill-downs exist (by reading the engine's own `breaches_threshold` flag) are presentation and routing; deriving a figure is not done. One consequence worth stating: Onboarding/CS efficiency renders as **touches per automated Action** — the metric tree's own orientation — rather than the Actions-per-touch inversion the illustrative sample readout showed, because inverting it here would be this artifact publishing a number no mart computed.
- **Model type selection and rationale (why there is no model)**: this artifact is pure assembly, so the question is not which model class but whether a model belongs here at all. Two candidates were considered and rejected. (1) A *scoring/prioritisation model* over the scorecard (ranking which of the eleven nodes most deserves leadership attention) would introduce a second, unvalidated opinion competing with the variance engine's own threshold rule — the engine already answers "which nodes earned a drill-down," and Section 5's drill-down section is specified as variable-length-by-breach, not top-N. (2) A *template-based prose generator* for the executive summary would produce text that reads as narrative while carrying none of the causal reasoning the section exists for; it is excluded on the same grounds the narrative itself is deferred (below). What remains is a structural/logic artifact in the sense `analytics-engineering-conventions` names — the same category as the variance-diagnostic engine and the segment-migration analysis — so **no coefficient table, no AUC, no confusion matrix, no calibration note and no R²/RMSE applies here, and their absence is deliberate, not pending.**
- **Point-in-time design**: `as_of_date` is a required parameter and is passed straight through to `run_diagnostic()`, whose loaders all filter `month <= as_of_date`. This module introduces no additional data access, so it introduces no additional leakage surface. The rendered document names both the `as_of_date` and the evaluation month it resolved to.
- **Determinism / seeding**: no stochastic step exists in this module — no sampling, no simulation, no train/test split — so no random seed applies, matching `analytics/segment_migration.py`'s and `analytics/variance_diagnostic.py`'s precedent. The one indirect exception is inherited: the watchlist section renders `analytics/health_score.py`'s scored output, seeded there via that module's `_RANDOM_SEED = 42`.

### Resolved scope decision — the reporting period is monthly, not weekly

The design brief's sample readout is weekly ("August 24 – August 30, 2026"). Every actuals mart in this project is segment × month, and the variance-diagnostic engine evaluates the last complete month at or before `as_of_date` (diffing a partial period's actual against a whole period's plan is a unit mismatch in disguise). A weekly readout over monthly marts would have to either re-window the marts inside this artifact — the one thing a pure-assembly artifact must not do — or repeat a single monthly figure under four weekly labels. **Resolved: the reporting period is the evaluation month**, and the rendered header says so in place of borrowing the sample's weekly framing. The artifact keeps the name "weekly executive readout" (the build spec's and Section 8's own name for it); the cadence question is a grain question about the marts, not a naming one.

This settles the input build spec Section 7's open threshold question was waiting on. The Variance-diagnostic engine entry's selectivity table records that ±8% flags ~83% of metric-months at monthly grain against the sample readout's illustrative 3-of-11 weekly cadence, and notes that resolving Section 7 "is a decision for the readout build, when the reporting period's grain is fixed." The grain is now fixed at monthly. **The threshold itself is not changed here**: it belongs to the variance-diagnostic engine, this artifact consumes it read-only, and ±8% remains PROPOSED per that entry. What this entry adds is the settled premise — any revision to the threshold should be argued at monthly grain, against that selectivity table, and made in the engine.

### Target — PROPOSED, not yet confirmed

No accuracy or error target applies (pure assembly, per the shape decision above). Three structural/trace criteria stand in its place, in the same spirit as the health score's stated AUC band but newly derived here, since nothing upstream states a number for an assembly artifact. All three are stated as **exact equality rather than a tolerance band**, and that difference from the health score's 0.65–0.80 range is the grounding, not an oversight: an AUC band exists because a fitted model's measured performance carries genuine sampling variance, whereas every check below is deterministic and re-derivable from the same inputs with no variance at all. A tolerance on any of them would imply an error source that does not exist, and would quietly license exactly the failure the criterion is meant to catch.

1. **Structural completeness: exactly 11 Layer-1 rows in the scorecard, every period, unconditionally — 11/11, no tolerance.** Build spec Section 5 says "all 11 nodes, every week." Any number other than 11 means a node was dropped or an intermediate node was admitted; both are defects, neither is drift. Includes the two nodes with no computable actual (`magic_number`, `am_efficiency`) and Activation's degenerate status — they are shown with their reason, not hidden.
2. **Drill-down cardinality fidelity: the drill-down count equals the number of scorecard rows with `breaches_threshold == True`, exactly, and the keys match in order.** Equality, not a band: "never padded to a fixed count" (Section 5) and "never truncated" are both violated by any inequality, in either direction. Zero is a valid result and renders as an explicit statement that nothing breached.
3. **Source-trace fidelity: 100% of the readout's numeric fields re-read identically from a freshly-run `run_diagnostic()`, at exact float equality.** Since assembly performs no arithmetic, a non-zero difference anywhere means a computation was introduced into the artifact that is specified not to compute — which would place that computation outside the validation of the artifact that owns it.

`analytics-model-validator` confirms or adjusts these three as the right criteria for an assembly artifact before they are treated as settled — they carry the same PROPOSED status the variance engine's ±8% threshold and the segment-migration analysis's 10% firmographic-rescore floor carry.

## Capacity planning

- **Built**: `analytics/capacity_planning.py`. Grain: one row per quota-bearing rep (ISR/AE) per **complete** calendar quarter in which that rep had at least one active day, quarter end ≤ `as_of_date`. Everything the module publishes — attainment, ramp-adjusted capacity, the achievability assessment — is an aggregation of that one panel. No dbt model was added or changed for this artifact, and no Phase 1 generator or raw table was added; quota history, rep status history and rep dimensions all already exist as real generated data.
- **What it is**: build spec item #3, the artifact that absorbs quota setting and attainment analysis — "is the quota mathematically achievable given capacity, not just headcount count." The distinction it exists to make is that **two teams with identical headcount and identical stated quota do not have identical real capacity if their ramp mixes differ**, and this module turns that from an assertion into a computed, decomposed number.
- **Scope — ISR/AE only, deliberately**: `generators/reps.py` scopes `quota_history` to ISR and AE ("the new-business, quota-bearing roles per build spec Section 2; AM comp isn't described as quota-based in either doc"), and `dim_reps` carries a null `quota_amount` for every AM and SE period. Quota attainment and quota achievability are therefore only meaningful concepts for ISR/AE. **AM headcount/book-size capacity is a related but distinct question and is not forced into a quota-attainment framing it does not have** — it already has a home in the metric tree (Onboarding/CS efficiency and AM efficiency, both `mart_efficiency` nodes, whose Layer-2 children name "book size, ramp status, check-in cadence" explicitly). This artifact does not duplicate or compete with it. SE carries no quota either and is likewise out of scope.
- **Relationship to the metric tree**: this is not a parallel concept to anything in the tree — it computes two nodes the tree already names. **"Rep capacity / ramp mix"** is a Layer-3 leaf under Win rate (Growth → New logo consumption revenue → Win rate), and this module's `ramping_quota_share` / `ramp_capacity_haircut` per team-quarter is exactly that leaf's ramp-mix quantity, now computable. **"Rep fully-loaded cost, incl. ramp"** sits under S&M cost in Magic Number's branch; this module supplies the *ramp* half of that leaf (which rep-quarters are ramping, and what fraction of capacity that costs) but **not** the cost half — no rep comp/cost source exists anywhere in Phase 1, which is the same gap that makes `magic_number` and `am_efficiency` structurally not-computable in `analytics/variance_diagnostic.py`. That gap is named here, not papered over with an assumed comp figure.
- **Shape decision — structural/descriptive, not predictive**: every number in this module is a direct computation from real empirical inputs (observed closed-won ARR, stated quota from `dim_reps`, hire dates, status history) plus one ramp rule taken verbatim from the build spec. Nothing is fitted; there is no train/test split, no estimated parameter, no probability. Per `analytics-engineering-conventions`' **"Structural/logic artifacts"** category — named there for the variance-diagnostic engine, applied here on the same reasoning the Segment migration entry uses — **there is no coefficient table, no R²/RMSE, no residual diagnostics, no AUC, no confusion matrix and no calibration note here, and their absence is deliberate, not pending.** This is stated explicitly rather than left as blank/TBD statistics fields, which would misleadingly imply they are still coming. Note this differs from the conventions doc's *expectation* that capacity planning would be a regression model ("Regression models (forecast, capacity planning — not yet built)"): that line was written before the data was examined. Against the data that actually exists, there is nothing here to regress — see the next bullet.
- **Model type selection and rationale (why not a fitted model)**: a regression predicting rep-quarter attainment from tenure, segment, quota level and headcount was the credible alternative and was rejected on three grounds. (1) **The ramp effect is already an exact known rule, not something to estimate.** Build spec Section 4 states it ("unramped reps at ~50% quota capacity for first 2 quarters") and `generators/config.py`'s `RAMPING_REP_WIN_ASSIGNMENT_FACTOR = 0.55` is the mechanism that makes it true in the data. A tenure coefficient fitted on this data would mostly be re-deriving the generator's own ramp rule — the same trivial-accuracy failure mode the Account health score entry's calibration note documents for scoring inside a deterministic decline window, and the same reason the Segment migration entry rejected a migration-propensity classifier. (2) **The quantity a planner needs is a sum, not a conditional expectation.** "Does this team's aggregate quota exceed its aggregate achievable capacity" is answered by adding up rep-level capacity; a fitted model would replace an exact sum with a noisy estimate of it, the same argument the Variance-diagnostic engine entry makes for walking a known arithmetic identity rather than fitting coefficients to it. (3) **Sample size does not support the alternative anyway** — 673 rep-quarters total, of which only 105 are ramping, spread over 2 rep types; a per-team fitted tenure effect would rest on ~50 observations each of a lumpy, low-count outcome (an AE closes ~0.35 deals per quarter, and 53.1% of all rep-quarters close zero). The empirical baseline this module computes instead is a single pooled ratio per team over all 268–300 ramped rep-quarters, which is the more stable read of the same data. A genuinely predictive rep-level artifact exists elsewhere in the portfolio — build spec item #14, "Rep productivity & coaching diagnostics," Wave 4 — and is not pre-empted here.
- **Inputs**, both read from dbt's marts layer:
  - `dim_reps` (`rep_id`, `rep_type`, `segment`, `hire_date`, `period_start_date`, `period_end_date`, `quota_amount`, `rep_status`) — one row per rep per capacity period, where a boundary is any date quota or status changed. This is the model the build spec Section 2 designates for exactly this purpose ("joined against `quota_history` and `rep_status_history` for point-in-time capacity queries").
  - `fact_opportunities` (`rep_id`, `is_won`, `amount`, `opportunity_type`, `owner_role`, `close_date`) — actual attainment: closed-won, `opportunity_type = 'new_business'`, ISR/AE-owned, summed by rep and close quarter. SMB's system-owned auto-won records and AM-owned renewal/expansion records are excluded (no quota attaches to either).
  - **Read-scope note, stated rather than assumed**: `analytics-engineering-conventions` says Phase 4 reads `mart_*` tables and never reaches into `stg_`/`int_`/raw. Both tables above are marts-layer models in the `main_marts` schema, so the rule's actual intent — no reaching around the modelling layer — is respected, and `int_rep_capacity_periods` (which `dim_reps` is built on) is deliberately *not* read directly. But no `mart_*`-prefixed table exposes rep-grain quota or rep-grain opportunity outcomes, so the stricter prefix-literal reading the Variance-diagnostic engine entry applies to `fact_revenue_monthly` would leave this artifact unbuildable. Resolved in favour of reading the designated dimension. **A `mart_rep_capacity` exposing the rep-quarter panel is the Phase 2 change that would close this cleanly**, and is worth doing before a second consumer needs the same panel; it is a mart gap, not a reason to reach around anything.
- **Ramp-capacity rule and its grounding**: a rep-quarter is classified `ramping` when the rep's tenure **at the quarter's midpoint** is under 180 days, `ramped` otherwise. Both halves are taken from existing artefacts rather than invented: 180 days is `generators/opportunities.py`'s own `_RAMP_FULL_DAYS`, the cutoff the data was generated against, and it is that file's reading of build spec Section 4's "first 2 quarters." The midpoint evaluation is this artifact's own resolved refinement — evaluating tenure at the quarter *start* makes the rule cover two quarters for a rep hired on the first day of a quarter but three for a rep hired on the last day, whereas the midpoint lands on exactly two quarters for every hire date.
- **Ramp-capacity discount: 0.50, adopted not invented.** Build spec Section 4 states the design assumption directly — "Unramped reps at ~50% quota capacity for first 2 quarters, any segment/role" — and that stated number is what the model applies. It is not taken on the spec's authority alone, because a discount nobody checked against the data would be decoration. `check_ramp_discount_reconciles()` measures what ramping reps actually produced per capacity-day of quota against what ramped reps produced, and confirms the two agree. **Observed pooled ratio: 0.488 at `as_of_date` 2025-12-31 (0.515 at 2025-06-30)** — i.e. a ramping rep really does deliver just under half a ramped rep's output in this data. This reconciles the three numbers in play rather than introducing a fourth: `RAMPING_REP_WIN_ASSIGNMENT_FACTOR = 0.55` is the *mechanism* (a ramping rep gets 0.55× a ramped rep's probability of being assigned a won deal), ~50% is the *stated assumption*, and 0.488–0.515 is the *realized outcome*. The realized figure lands slightly under 0.55 because that factor is a relative weight inside an assignment pool, not a direct multiplier on a rep's output. Per rep_type at 2025-12-31: **AE 0.529, ISR 0.280** (AE 0.558 / ISR 0.271 at 2025-06-30). ISR sits further below the rule than AE; with 46–48 ramping ISR rep-quarters against a lumpy low-count outcome this is within what that sample supports, and the pooled figure is the one the reconciliation check is stated on.
- **Capacity-day weighting (why the ramp ratio is not simply "ramping ARR ÷ ramped ARR")**: ramping reps average **~0.81 of a quarter on seat** — they are hired mid-quarter by definition — so an unadjusted comparison would charge partial tenure to the ramp effect and overstate it by roughly a fifth. Every baseline and every ratio in this module is weighted by `capacity_day_quota` (`stated_quota × coverage_share`), so partial tenure and ramp status are measured as separate things. Stated quota itself is **never** pro-rated: the generator does not reduce it for ramp or for a mid-quarter start, and quota diverging from achievable capacity is precisely what this artifact exists to measure.
- **Quota grounding — the stated quota this artifact measures against is itself derived, not guessed.** `generators/reps.py`'s `_QUOTA_BASE_RANGE` is back-solved from the opportunity generator's realized deal supply over the fully-supplied window (2023-01 onward, the first quarter in which `opportunities.py` generates lost pipeline as well as won deals), measured on fully ramped rep-quarters only: **AE — 2.01 closed new-business opportunities per ramped rep-quarter × 20.98% realized win rate × $250,804 average won deal = $103,619 of ARR per ramped rep-quarter; ISR — 5.98 × 25.85% × $22,595 = $34,363.** Each band's midpoint is that anchor divided by the mean realized step-up multiplier over the window (~1.25×), so the *stated* quota lands on the anchor: AE $60,000–105,000 base (midpoint $82,500, −0.4% off the derived $82,858), ISR $22,500–33,000 (midpoint $27,750, +0.5% off $27,601). Band half-widths carry over from the prior ranges unchanged (AE ±27.3%, ISR ±18.9%) — rep-to-rep quota differentiation is real practice and was never the defect; only the level was. **Resolved decision on the target band**: quota is set *at* a fully ramped rep's realized quarterly production, so a ramped rep on seat all quarter expects ~100% attainment and company-wide blended attainment lands in the mid-80s to mid-90s once ramping and partial-tenure rep-quarters fold in. That is the conventional SaaS shape — a target at, not far above, median rep capacity, genuinely missed and genuinely beaten. It is not set higher because it cannot be: total AE new-business pipeline is **452 opportunities across the whole simulation**, so even at a hypothetical 100% win rate the supply caps what any AE roster can produce (452 × $256,122 = $115.8M). **Realized shape at `as_of_date` 2025-12-31**: company-wide attainment **84.4%** across all 28 quarters and **94.8%** over the fully-supplied 2023+ window (AE 94.9%, ISR 94.6%); across 151 complete rep-years, median **75.7%**, mean **87.0%**, **36.4% at or above 100%** (46.6% over 2023+), max 456.7%. Quarter to quarter the company figure swings from **74.1%** (2025-Q2) to **132.9%** (2025-Q4) — variance above and below, which is what a real target produces.
- **Empirical baseline productivity, derived not assumed**: the baseline is the attainment a *fully ramped* rep of a given `rep_type`/segment actually achieves per capacity-day of quota — observed ramped won ARR ÷ observed ramped capacity-day quota. **At `as_of_date` 2025-12-31: AE 0.9689 (n = 268 ramped rep-quarters), ISR 0.8016 (n = 300), pooled 0.9245 (n = 568).** Expected achievable capacity per rep-quarter is then `stated_quota × baseline_attainment × coverage_share × ramp_factor`, where `ramp_factor` is 0.50 while ramping and 1.0 once ramped. A baseline near 1.0 is the expected consequence of `_QUOTA_BASE_RANGE` being back-solved from ramped-rep deal supply (see the quota-grounding bullet below) — a ramped AE on seat all quarter is now expected to land near quota, which is what a quota is for. ISR sits lower because the baseline spans the full panel including the thin 2020–2022 back-dated era; restricted to the fully-supplied 2023+ window the two teams are level (AE 0.987, ISR 0.988).
- **Two baseline modes, both point-in-time honest** (`compute_ramped_baseline(mode=...)`):
  - `as_of_date` (default, and what the build-time checkpoint reports) — one baseline per team estimated over every complete quarter up to `as_of_date`, applied uniformly. The descriptive read. Two runs at different `as_of_date`s can legitimately assign the same quarter different capacity, because the baseline is itself an as-of estimate; that is stated rather than hidden.
  - `prior_quarters_only` — an expanding window using only quarters strictly *before* the quarter being evaluated, so a quarter's quota is never judged against that same quarter's own realized productivity. The forward-planning read. Reported as NaN until 8 ramped rep-quarters accumulate rather than computed off a handful of lumpy Enterprise deals. **The two modes converge closely** (final-quarter baselines: AE 0.9231 vs. 0.9689, ISR 0.8017 vs. 0.8016), which is the evidence that the default mode's in-sample baseline is not materially circular.
- **Segment × rep_type is a degenerate cross in this data**, and saying so avoids implying more resolution than exists: ISR maps 1:1 to Commercial and AE 1:1 to Enterprise (`generators/reps.py` assigns segment by role), so grouping by (segment, rep_type) yields the same partition as rep_type alone. SMB has no rep at all. The module keys on both because that is the grain the question is asked at, not because they vary independently.

### The achievability diagnostic — a three-way gap decomposition, and two comparison bases

For each team-quarter (segment × rep_type) and company-wide, `assess_quota_achievability()` sums the team's stated quota from its active reps' `dim_reps` rows and its ramp-adjusted expected capacity, and decomposes the gap into three **exactly additive** parts:

| Component | Formula | What it isolates |
|---|---|---|
| `productivity_gap` | `quota × (1 − baseline)` | The shortfall that would exist even with every rep fully ramped and on seat all quarter — i.e. the quota's own level vs. what a ramped rep produces |
| `coverage_gap` | `quota × baseline × (1 − coverage)` | Selling time lost to mid-quarter hires and departures |
| `ramp_mix_gap` | `quota × baseline × coverage × (1 − ramp_factor)` | **The ramp-mix effect specifically** — the capacity two same-headcount teams differ by purely through who is ramping |

Two comparison bases are reported, and the difference between them is load-bearing:

- **`quota_coverage_ratio` = expected capacity ÷ stated quota** — the literal answer to "is the quota mathematically achievable." Flagged **`comparable`**. Quota and capacity are denominated in the same units because `generators/reps.py`'s `_QUOTA_BASE_RANGE` is back-solved from the opportunity generator's own realized deal supply — opportunities closed per ramped rep-quarter × realized win rate × average won deal size — so this ratio reads as capacity, not as a gap between two independently-parameterised generators. **Observed coverage runs 0.565–0.969 across the 48 evaluated team-quarters (median 0.771), and 34 of 48 exceed the 15% margin** at a quota-over-capacity gap of 3.2–77.1%. The residual gap is a real capacity reading with two named sources: the ramp haircut, and — for the 2020–2022 team-quarters — an opportunity supply that had not yet reached steady state. From 2023 onward the AE team clears the margin in **every one of its 12 team-quarters** (coverage 0.885–0.969) while ISR clears none (coverage 0.736–0.802), which is a difference between two teams the diagnostic can now actually state. **This basis was previously flagged `level_caveated`**: quota was sized from a plausibility heuristic against `config.ACV_RANGES` with no reference to deal volume, coverage ran 8.5–14.5%, all 48 team-quarters failed, and the number measured the definitional mismatch rather than capacity. That mismatch is now closed at the source rather than caveated downstream — see the quota-grounding bullet above and `CHANGELOG.md`.
- **`ramp_attributable_gap_pct` = `ramp_mix_gap` ÷ expected capacity** — the level-immune basis, and the one that carries the artifact's actual signal. A constant offset in the baseline cancels out of this ratio entirely, in the same way the variance engine's trailing-baseline signal is immune to its caveated plan-level offsets. This is what distinguishes a ramp-mix problem from a quota-level problem.

**Achievability margin: 15% — PROPOSED, not yet confirmed.** A team-quarter is flagged when stated quota exceeds ramp-adjusted expected capacity by more than 15% of that capacity. Nothing upstream (build spec, QA plan, metric tree) states a number for this, so it is this artifact's own proposal at build time, carrying the same PROPOSED status as the variance engine's ±8% threshold and the segment-migration analysis's 10% firmographic-rescore floor. **Grounding, corrected**: the margin gates `ramp_attributable_gap_pct` (`ramp_mix_gap ÷ expected_capacity`), and the empirical ramped-attainment baseline — the one estimated quantity in this artifact — cancels out of that ratio exactly (a constant per-team-quarter factor in both numerator and denominator), confirmed by recomputing the ratio with the baseline term algebraically removed and matching the module's own column to 5.5e-17. So the baseline's estimation precision is not what this margin is actually protecting against, and citing its relative standard error as the grounding was wrong. The real grounding is **selectivity and robustness**: 15% flags 13 of 48 team-quarters — neither near-zero nor near-universal — and that result is stable across a wide band of the one input the ratio does depend on, the ramp-capacity discount itself (breach count moves only from 14 to 10 across discount values 0.40–0.60, and the 13-of-48 result holds exactly across the discount's own reconciled range of 0.488–0.500). A margin sitting on a flat part of that selectivity curve, rather than a knife-edge, is a defensible floor even without a precision argument behind it.

**Result at `as_of_date` 2025-12-31** (48 team-quarters with genuine opportunity supply):

| Basis | Flagged | Reading |
|---|---|---|
| `quota_coverage_ratio` (absolute, `comparable`) | **34 of 48** | Real capacity reading: ramp haircut plus the 2020–2022 era's pre-steady-state opportunity supply. Splits cleanly by team from 2023 on — AE 0 of 12, ISR 12 of 12 |
| `ramp_attributable_gap_pct` (level-immune) | **13 of 48** | The ramp-mix signal specifically, and genuinely selective. Unchanged by the quota recalibration, as the level-immunity claim predicts |

The 13 breaches are all concentrated in the 2020-Q1 → 2022-Q3 build-out era, when ramping reps carried **27–64% of team quota** (max ramp-attributable gap **44.5%**, at 2021-Q2 Enterprise: 6 AEs of whom 4 were ramping, so the team held only 69% of the capacity its headcount implied). **Not one quarter from 2023 onward breaches** — by then each team carries 0–3 ramping reps out of 14–21 and the ramp-attributable gap falls to 0–7.19%, still comfortably under the 15% margin in every one of those 24 team-quarters. That contrast is the artifact working: same diagnostic, same threshold, firing hard on a ramp-heavy roster and staying quiet on a mature one. Median ramp-attributable gap across all 48 team-quarters is 4.4%.

### Point-in-time design

Every function takes `as_of_date` and it is honoured on all three data surfaces. `dim_reps` periods are filtered to `period_start_date <= as_of_date` (a period beginning later is future information — a future quota raise or a departure not yet known). Opportunity data is filtered to `close_date <= as_of_date`. Only **complete** quarters are admitted to the panel (`quarter_end <= as_of_date`): a partial quarter's realized ARR measured against a whole quarter's stated quota is a unit mismatch in disguise, the same reason `analytics/variance_diagnostic.py` evaluates the last complete month rather than a part-month. **No stochastic step exists in this module** — no train/test split, no sampling, no simulation — so no random seed applies, matching `analytics/segment_migration.py`'s and `analytics/variance_diagnostic.py`'s precedent.

**Data-window guard.** `generators/reps.py` back-dates ~65% of hires to before the account generator's earliest possible account, so the earliest rep-quarters carry a real stated quota against a market that does not yet exist in the data. `load_opportunity_supply_window()` derives the first quarter containing any ISR/AE new-business opportunity (2020-Q1) from `fact_opportunities` itself rather than hardcoding a generator constant, and every achievability row carries `has_opportunity_supply`. **4 company-quarters (all of 2019) are flagged False** — their attainment is structurally zero and says nothing about capacity. They are reported with the flag rather than dropped silently, the same treatment the variance engine's `data_window` block gives its end-of-window truncation.

### Validation — structural tie-outs and a non-vacuousness check, not statistics

In place of an accuracy/error target (none applies — see the shape decision), five checks in `run_build_time_validation()`. Three are exact structural invariants in the spirit of the segment-migration analysis's growth-bridge tie-out (the decomposition tie-out runs in both baseline modes, since only `prior_quarters_only` exercises the not-yet-estimable `NaN` path); two confirm the ramp mechanism this model is built on is real in the data rather than an assumption the model quietly assumes into existence. **All 5 pass at both checkpoints** (`as_of_date` 2025-12-31 and 2025-06-30).

| Check | What it pins down | Floor / tolerance | Result (2025-12-31) |
|---|---|---|---|
| `attainment_reconciles_to_fact_opportunities` | The rep-quarter panel's `won_arr` sums to exactly the closed-won new-business ARR `fact_opportunities` reports for ISR/AE-owned deals in the same complete quarters — no dollar dropped (a win with no matching `dim_reps` period) and none double-counted (a rep with several capacity periods inside one quarter fanning out the join, a real risk given `dim_reps`' period grain) | ≤ $0.01 max abs diff, both in total and row-by-row | **$0.00**, 0 unmatched rep-quarters, $37,212,986.21 / 478 deals both sides |
| `capacity_gap_decomposition_is_exact` | `productivity_gap + coverage_gap + ramp_mix_gap == stated_quota − expected_capacity` for every team-quarter. ### Target and drift threshold

- **Target**: no accuracy/error target applies (structural/descriptive). The five checks above stand in its place, and the three exact tie-outs are stated as **hard invariants with a floating-point tolerance rather than a band** — the same reasoning the Weekly executive readout entry gives for stating exact equality: deterministic arithmetic has no sampling variance, and a tolerance would imply an error source that does not exist.
- **Drift threshold**: per the doc's general rule, 2 consecutive monthly checkpoints failing any of the five checks → flagged for review. In practice the three tie-outs are expected never to breach (structural invariants — a breach is a defect to fix, not a trend to watch). Two are genuinely worth watching in `fact_model_performance_history`. **`empirical_ramp_ratio_pooled`**: if it drifted outside 0.40–0.60, the 0.50 discount would no longer describe the data and the capacity model would need re-grounding rather than re-running. **`ramped_baseline_attainment_pooled`**: now that quota is back-solved from deal supply, this figure should sit near 1.0 (0.9245 at 2025-12-31); drifting outside 0.70–1.30 means quota and the supply that fills it have decoupled again and `_QUOTA_BASE_RANGE` needs re-deriving at the generator, not compensating for downstream. Both are natural `drift-monitor` hooks for this artifact.
- **Persistence**: scalar time-series metrics logged to `fact_model_performance_history` via `analytics/model_performance.py`'s `log_performance()` — `structural_checks_total`/`_passed`, `ramp_capacity_discount_applied`, `achievability_margin`, `empirical_ramp_ratio_pooled`/`_ae`/`_isr`, `ramped_baseline_attainment_pooled`/`_ae`/`_isr`, `ramped_rep_quarters_pooled`, `ramping_rep_quarters_pooled`, `team_quarters_evaluated`, `team_quarters_quota_not_achievable`, `team_quarters_ramp_mix_breaches_margin`, `max_ramp_attributable_gap_pct`, `company_quota_coverage_ratio_latest_quarter`, `company_ramp_capacity_haircut_latest_quarter`, `company_attainment_latest_quarter`, and both reconciliation max-abs-diffs. The variable-width tables (attainment by team-quarter, achievability detail, the ramp-effect breakdown) do not fit that log's flat scalar grain, per `analytics-engineering-conventions`' Persistence note, and are the structured detail recorded in this entry instead.

### Known limitations

- **The absolute achievability verdict now rests on the 2023+ window's deal supply being representative of the whole panel.** `_QUOTA_BASE_RANGE` is derived from the fully-supplied window, but the same quota level is applied to the 2020–2022 build-out era, whose opportunity supply had not reached steady state. That is why 22 of 24 pre-2023 team-quarters exceed the margin against 12 of 24 from 2023 on. The residual is a real capacity reading, not a units mismatch, but it is a reading of a data window as much as of a roster. The two ratios are not independent by construction either — quota is calibrated so a ramped rep lands near 100%, so `quota_coverage_ratio` will always sit near `baseline × coverage × ramp_factor`. That is the intended design (a quota *should* be set at capacity), not a hidden circularity, but it means the absolute basis answers "how far is this team from a correctly-set quota," not "is the quota level itself right" — the level is right by derivation. `ramp_attributable_gap_pct` remains the basis that carries information the calibration does not put there.
- **No rep cost data exists anywhere**, so the tree's "Rep fully-loaded cost, incl. ramp" leaf remains only half-computable from this artifact (the ramp half). Same root gap that leaves `magic_number` and `am_efficiency` not-computable in the variance-diagnostic engine; it closes with a Phase 1 comp/cost source, not a Phase 4 workaround.
- **ISR's empirical ramp ratio (0.280) sits well below the AE figure (0.529) and below the 0.50 rule.** With 46–48 ramping ISR rep-quarters against a low-count, lumpy outcome, the module applies the pooled-reconciled 0.50 to both teams rather than fitting a per-team discount off that sample. A per-team discount becomes defensible if more ramping ISR history accumulates; there is no basis for it on this snapshot.
- **No forward-looking capacity projection.** This artifact assesses quarters that have closed. Projecting next quarter's capacity from a planned hiring ramp is a natural extension the `prior_quarters_only` baseline mode already provides the seam for, but it is not built here — it would need a hiring plan, which is not in any source.
- **No mart exposes the rep-quarter panel.** Every consumer that wants it currently has to re-derive it through this module. `mart_rep_capacity` is the Phase 2 change worth making before a second consumer appears.

## Data quality / metric governance

- **Built**: `analytics/data_quality_governance.py`. Grain: one governance run per `as_of_date`, three independent check families each at their own natural grain (one row per metric-tree edge; one row per mart/column/table for the data-quality checks; one row per invariant rule) — everything the module publishes is one of those three families plus a synthetic self-check. Report written to `analytics/outputs/data_quality_governance_<as_of_date>.json` / `.md` (version-controlled, matching the Weekly executive readout's precedent for a real-data document being inspectable without rebuilding the pipeline). No dbt model was added or changed for this artifact, and no Phase 1 generator or raw table was added.
- **What it is**: build spec item #18, Wave 3 ("infrastructure before more gets built on ungoverned data"). Three distinct jobs, none of which any other artifact does:
  1. **Metric-tree mathematical integrity.** For every parent node in `docs/acme-corp-gtm-metric-tree.md` that states a sum/product/ratio formula over its children, computationally verify the built marts actually satisfy that equation, in real values, at `as_of_date`. This operationalizes `CLAUDE.md`'s invariant ("every parent metric must be the actual mathematical result of its children... never a 'related metrics' grouping") as a runnable check instead of a design promise.
  2. **Marts-layer data quality.** `docs/acme-corp-phase1-data-qa-plan.md`'s test suite (referential integrity, distributional realism, volume sufficiency) covers raw generator output only. Nothing previously re-ran an analogous check against the dbt-*built* marts, which a dbt bug could still corrupt after raw generation passes clean. This closes that gap, at the marts layer specifically.
  3. **Invariant governance.** `CLAUDE.md`'s "Non-negotiable invariants" section is a set of design promises (segment terminology, no downgrade path, USD only, channel/segment orthogonality, the four `trigger_reason` values, no independently-random risk columns). This mechanizes each one into a check against the live built data, including three data-grounded spot-checks — not a generic assertion — that win probability, churn probability and usage growth each carry a real relationship to a stated driver.
- **Explicitly not a duplicate of `drift-monitor`**: `drift-monitor` is recurring *production* monitoring of a *fitted* model's calibration drift and Layer-3-to-Layer-2 proxy-metric decoupling (per this doc's "Proxy-metric decoupling — general rule"), checked against a stated drift threshold over time. Nothing in this artifact is fitted, and nothing here tracks decay over a time series — every check is a one-shot, deterministic comparison against already-materialized values or a fixed rule, re-run fresh at whatever `as_of_date` is asked for. The overlap that might look like duplication and isn't: `drift-monitor` asks "has this model's accuracy degraded since it was built," while this artifact asks "does the built data actually satisfy the arithmetic/structural contract it always claimed to." A metric-tree edge that fails here is a correctness bug (something to fix), not a drift event (something to watch trend on) — the distinction the Variance-diagnostic engine entry draws between a deterministic tree walk and a fitted attribution model applies here for the identical reason.
- **Shape decision — structural/logic artifact, not predictive**: every check is a deterministic comparison — either an exact arithmetic identity (tolerance is floating-point noise, not a statistical band), a referential-integrity anti-join, a null-rate threshold, or a two-sample comparison with a stated, PROPOSED floor. Nothing is fitted; there is no train/test split, no estimated parameter, no probability model. Per `analytics-engineering-conventions`' **"Structural/logic artifacts"** category — the same reasoning the Variance-diagnostic engine, Segment migration analysis, Capacity planning and Marketing attribution entries all use — **there is no coefficient table, no AUC, no confusion matrix, no R²/RMSE and no calibration note here, and their absence is deliberate, not pending.**
- **Model type selection and rationale (why not a fitted anomaly/drift-detection model)**: a statistical anomaly detector (e.g., flagging a mart value as suspect when it falls outside its own historical distribution) was the credible alternative and was rejected on two grounds specific to this artifact's job. (1) **Most of what this artifact checks is a known, exact identity, not an unknown distribution.** The metric tree's parent-child formulas are stated exactly (sum/product/ratio); CLAUDE.md's invariants are stated exactly (three segment values, two allowed migration directions, four trigger reasons). Fitting a distribution to detect deviation from a quantity that has an exact, already-known correct answer would replace a certain check with an uncertain one — the same argument the Variance-diagnostic engine entry makes for walking a known arithmetic identity rather than fitting coefficients to it, and Capacity planning's entry makes for summing rather than regressing. (2) **A historical-distribution anomaly detector needs history this artifact doesn't have yet** — this is the first checkpoint of a governance run that has never existed before, so there is no trailing distribution of "normal" to compare a new checkpoint against. `fact_model_performance_history` accumulating checkpoints over time is exactly the mechanism that *would* eventually support that kind of check — and is `drift-monitor`'s job, not this artifact's, once enough checkpoints exist.
- **No random seed applies.** No stochastic step exists anywhere in this module — no train/test split, no sampling, no simulation — matching `analytics/segment_migration.py`'s, `analytics/variance_diagnostic.py`'s and `analytics/capacity_planning.py`'s precedent. The one place a seed appears at all is inside `run_synthetic_violation_tests()`'s independently-random negative-control scenario (`np.random.default_rng(42)`), which exists only to construct a synthetic "this column really is random noise" case for the self-check suite — seeded for reproducibility like every other stochastic step in this project, even though it produces no business output.
- **Point-in-time design**: every loader takes `as_of_date` and filters `month <= as_of_date` / `close_date <= as_of_date` / `effective_date <= as_of_date` / `migration_date <= as_of_date` as appropriate to each source mart's own grain; `dim_accounts` and `dim_reps` (current-state / point-in-time-period dimensions) are filtered on `signup_date <= as_of_date` and `period_start_date <= as_of_date` respectively, the same treatment `analytics/capacity_planning.py` gives `dim_reps`. No table here is read without a point-in-time filter where the table's grain supports one.

**A genuine calibration decision worth stating**: the churn-probability spot-check is gated on the **median**, not the mean, relative decline. Confirmed at build time: `actions_consumed`'s median relative decline is 0.64 against a mean of only 0.13, even though 71% of churned accounts individually clear the 0.20 floor. The distribution carries a fat left tail — a minority of accounts with a near-zero usage baseline the whole way through, where a tiny absolute uptick right before churn reads as an enormous negative "decline" (the most extreme synthetic-looking case in the real data: −11.96, i.e. usage roughly 13× its own baseline in the final 3 months) — that drags the mean well below the population's typical behavior. The median is the honest summary of a distribution shaped like this one; gating on the mean here would have been measuring outlier noise, not the real driver relationship the check exists to confirm. `login_count`'s mean and median are much closer together (0.46 vs. 0.58) and both clear the floor regardless of which is used.

### Floors and thresholds — PROPOSED, not yet confirmed

None of these numbers are stated anywhere upstream (build spec, QA plan, metric tree); each is this artifact's own resolved decision at build time, in the same spirit as the Variance-diagnostic engine's ±8% and the Segment migration analysis's 10% firmographic-rescore floor:

- **`trigger_reason` minimum count floor: 20.** Chosen to sit far below every value observed at build time (245–7,222 across the four values), so ordinary future data regeneration can't spuriously trip it, while still being large enough that a single stray row can't fake compliance.
- **ACV outlier ceiling: 2× the segment's documented upper ACV bound.** Deliberately loose (corruption-catching, not business-realism) — the QA plan already owns the tighter distributional-realism band; this only needs to catch a value that's actually broken.
- **Win-probability spot-check: ≥15pp gap at z≥2.58.** The z-threshold matches `analytics/marketing_attribution.py`'s own holdout-suppression check (99% one-sided confidence), reused here for consistency across the repo's two-proportion comparisons rather than picking a new number.
- **Churn-probability spot-check: ≥0.20 median relative decline.** Conservative — Phase 3's own churn analysis observed usage dropping roughly 66%→23% (a ~65% relative decline) over the run-up to churn, so this floor sits well below the actual effect size and is unlikely to be spuriously tripped by ordinary noise.
- **Usage-growth spot-check: ≥1.5× the non-migrating population's growth rate.** Deliberately modest given the observed effect is far larger (9.1× and 8.5× at the two checkpoints) — the floor exists to catch a real regression, not to sit close to the observed value.

None of these is a validated statistical bound the way the health score's AUC target or capacity planning's achievability margin were checked against sampling noise — they are, honestly, judgment calls sized against the one real dataset this project has. `analytics-model-validator` is asked to sanity-check each against the same reasoning the Segment migration analysis's 10% floor was checked against (does the floor sit on a flat, non-knife-edge part of the observed range).

### Persistence

Scalar summary counts (`checks_total`/`_passed`/`_failed`, `metric_tree_edges_checked`/`_passed`/`_not_computable`, `referential_integrity_checks_total`/`_passed`, `completeness_checks_passed`, `distributional_sanity_checks_passed`, `volume_sufficiency_checks_passed`, `invariant_checks_total`/`_passed`, `synthetic_violation_scenarios_passed`/`_total`) are logged to `fact_model_performance_history` via `analytics/model_performance.py`'s `log_performance()`. The variable-width detail (per-edge results, per-FK-pair/per-column results, per-invariant detail, the full synthetic-scenario table) does not fit that log's flat scalar grain and is the structured detail recorded in `analytics/outputs/data_quality_governance_<as_of_date>.json`/`.md` and in this entry instead, per `analytics-engineering-conventions`' Persistence note.

### Target and drift threshold

- **Target**: no accuracy/error target applies (structural/logic artifact). The three check families above (53 checks total at 2025-12-31: 11 metric-tree edges + 34 marts-layer data-quality checks + 8 invariant checks) plus the 10-scenario synthetic self-check stand in its place — **all 53 real-data checks and all 10 synthetic scenarios pass at both checkpoints.**
- **Drift review trigger**: per this doc's general rule, 2 consecutive monthly checkpoints with any real-data check failing → flagged for review. In practice most of these checks are structural invariants expected to never fail on correctly-built data (a failure is a defect to fix, not a trend to watch, the same treatment Capacity planning's exact tie-outs get) — the two genuinely worth watching in `fact_model_performance_history` over time are `metric_tree_edges_not_computable` (should only ever *decrease*, as Phase 1/2 gaps close — an increase would mean a mart regressed) and the three not-independently-random spot-check margins (`win_probability` gap/z, `churn_probability` median decline, `usage_growth` ratio) — a real narrowing of any of those margins over time, even while still technically clearing its floor, would be the leading indicator that a generator or dbt change had quietly weakened a causal relationship this project's other artifacts depend on existing. This is a `drift-monitor` hook, not something this build-time run itself tracks over time.

### Known limitations

- **The `trigger_reason` floor, ACV ceiling, and the three spot-check floors are all first-checkpoint judgment calls**, not statistically derived the way the health score's AUC target or capacity planning's achievability margin were. They are stated explicitly as PROPOSED and handed to `analytics-model-validator` rather than treated as settled.
- **The metric-tree integrity checker covers every edge that has a stated formula in the tree text, but the tree also contains many Layer-2/Layer-3 nodes that are single measurements, not decompositions of listed children** (e.g. Avg initial commitment, Activation's own TTFA figure) — those have nothing to mathematically tie out and are correctly absent from the edge list, not silently skipped; `analytics/variance_diagnostic.py`'s own coverage table is the fuller inventory of which Layer-2/Layer-3 leaves are computable at all versus which have a real formula to check.
- **This is a first build-time checkpoint, not a monitored series yet.** `fact_model_performance_history` now carries two checkpoints (2025-12-31, 2025-06-30) for this artifact; a governance check that has only ever been run twice on a green build has not yet been tested against a real regression. The synthetic injected-violation suite is the substitute evidence that the mechanism works, per the shape decision above — it is not a substitute for eventually seeing this artifact catch something real.
- **No check here re-validates the Phase 1 QA plan's own test suite** (raw-generator-layer checks) — this module starts at the dbt-built marts layer, deliberately, since the QA plan already owns raw-layer correctness and re-running it here would be duplicative, not additive governance.
