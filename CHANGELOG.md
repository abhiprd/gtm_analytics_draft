# Changelog

All notable changes to this project are documented here. Format follows [Keep a Changelog](https://keepachangelog.com/en/1.1.0/).

## [Unreleased]

### Fixed
- `CLAUDE.md`'s non-additive-metric invariant named only Brand & Awareness as the deliberate exception to "every parent metric is the mathematical result of its children," while the metric tree's own text has always also carved out Marketing–sales handoff quality with equivalent non-additive language ("diagnostic overlay... not a fourth multiplicative factor"). The invariant, `README.md`'s duplicate of it, and `semantic/README.md`'s guardrail description now name both
- `semantic/server.py`'s fuzzy `did_you_mean` suggestions missed common acronym/spelled-out forms (`"net revenue retention"`, `"CAC"`) because character-level matching favored an unrelated metric sharing more letters (e.g. `logo_retention` over `nrr`) — never a wrong answer, since rejection was always correct, but a misleading suggestion. A small alias table is checked before the fuzzy fallback

- `opportunities.forecast_category` is now generated as the deal's final close-time forecast call rather than as a restatement of the outcome plus independent noise. Previously every won deal was stamped `Commit` unconditionally and every lost deal drew from `rng.choice(["Best Case", "Pipeline", "Omitted"], p=[0.3, 0.4, 0.3])` — a draw connected to no deal characteristic at all, violating the causal-wiring invariant, and a `Commit ⟺ won` mapping that made the field a perfect separator in both directions (Commit 100% won, every other category 0% won). It is now assembled as a perceived win probability on the log-odds scale from drivers already decided at the call site and cut into the same four-value vocabulary at the same conventional pipeline-review bands `fact_forecast_submissions` uses (0.70 Commit / 0.40 Best Case / 0.15 Pipeline). New business is driven by cycle depth within `config.CYCLE_LENGTH_DAYS` (the available progression proxy, since every deal emits the full `config.NEW_BUSINESS_STAGES` list and the stage dates derive from `cycle_days`), loss reason (`price`/`competitive` as a late slip off a confidently-carried deal, `no_decision` as the stalled deal nobody forecast), Enterprise POC outcome, discount position within `config.DISCOUNT_RATE_RANGE`, and rep ramp status as an optimism bias on the call. Renewal/expansion starts from the complement of `config.ANNUAL_CHURN_RATE` and is moved by the contract outcome (expansion / flat / contraction / churned), loss reason, notice-period runway, and the same ramp bias. Win rate by category rank is now monotone and non-degenerate at every cut — overall **Omitted 1.29% (n=465) → Pipeline 5.25% (n=476) → Best Case 27.23% (n=382) → Commit 98.89% (n=8,492)**; Commercial/Enterprise new business alone 0.48% → 1.86% → 15.87% → 81.96%; renewals alone 8.00% → 36.17% → 80.00% → 99.60% — so a Commit slips 94 times and a written-off deal closes anyway 31 times across the window. The ramp bias surfaces as an emergent property: a ramping rep's Commit converts at 87.0% against a ramped rep's 95.9%. SMB new business and migration-driven expansions remain unconditional `Commit` by construction and are now documented as such — a same-day self-serve signup has no forecast cadence to have made a call in, and a migration expansion formalises a committed minimum the account's own usage has already crossed, so neither has a losing branch. The new logic draws exclusively from a dedicated `np.random.Generator` seeded `BATCH2_SEED + 600`, threaded into `generate_new_business_opportunities()` and `generate_renewal_opportunities()` as a separate parameter — the same stream isolation `reassign_orphaned_ownership()` already gets — and the two retired draws are still taken from the shared sequential `rng` and discarded so its position is unchanged. All seven batch-2 outputs were regenerated and diffed column-by-column against the prior files: `forecast_category` in `opportunities.csv` is the only value that moved, and `opportunity_stage_history.csv`, `usage_monthly.csv`, `fact_workflow_chain_events.csv`, `subscriptions.csv`, `mrr_by_account_month.csv` and `committed_vs_utilized_monthly.csv` are byte-identical. Adds two correlational-validity checks in `tests/test_phase1_batch2.py` (monotone, non-degenerate win rate by rank; loss-reason ordering and the ramping-rep Commit conversion gap) and, in `docs/acme-corp-phase1-data-qa-plan.md`, a `Funnel & opportunities` edge case plus the matching correlational-validity test case. `fact_forecast_submissions` is unaffected — it never reads this column, and `test_close_time_only_fields_are_not_read` still passes unchanged
- Forecast's ML lens dropped `days_to_period_end` (days from the evaluation date to its quarter's end) after independent review found it a genuine point-in-time defect rather than a tuning choice: in training every row carries its own evaluation date, so the feature varies and appears informative, but the signal is deal-close-date position within the quarter — a post-close attribute leaking backward. At scoring time every open deal shares one `as_of_date`, so the feature is constant across the whole scored population, contributing zero discrimination while still applying a fixed log-odds offset to every production prediction. Removing it moved the canonical checkpoint's held-out AUC only slightly (0.8098 → 0.8153) and cut the ML lens's aggregate backtest under-forecast bias from −12.13% to −5.29% — direct evidence of a real production-time bias, not just an in-sample artifact. The removal did not explain a separate AUC-ceiling breach at a second checkpoint (0.8613 → 0.8593, still over the 0.85 target); that breach's methods-doc explanation ("holdout composition — a higher renewal share") was independently checked and found factually wrong (renewal share was actually near-identical, marginally lower), and is restated as a genuine, unexplained breach. The leak-ratio diagnostic's own reasoning ("identical ratios at both checkpoints ⇒ composition, not leakage") is corrected as a non-sequitur — the leak-proof baseline is built from inputs disjoint from the model's features, so it cannot detect a leak living inside those features, and a persistent leak would produce the same "identical ratio" signature. A proposed ratio-based AUC ceiling is rejected on the same grounds (it would not have fired at either checkpoint, including the one with a real unexplained anomaly); a composition-standardized within-stratum AUC is added as a diagnostic instead. Several numeric doc inaccuracies are also corrected (a count-weighted vs. dollar-weighted category-close-rate mismatch, a stale quarter count, a discount-rate population mismatch, coefficient/confusion/calibration figures refreshed for the corrected feature set)
- Marketing attribution's `pipeline_generated_formula_is_exact` check was an algebraic tautology — `channel_to_lead_rate` is defined as `leads_created / channel_volume`, so the three-factor product telescopes back to a lead count for any input values, and corrupting `channel_volume` by 1000× still passed. Replaced with `pipeline_generated_rollup_reconciles_to_source`, which independently re-queries `fact_leads`/`fact_campaign_engagement_events` via fresh SQL and checks both that against the rollup's own aggregates and an accounting identity (resolved + open == created) that can genuinely fail. Also corrected a docstring claiming `pipeline_generated` (the created-cohort basis) equals the converted-lead count "by construction" — true only when a period has no open (unresolved) tail, false on 12 of 116 real rows by up to 3,326 leads. The build spec's 0.3% campaign-spend reconciliation figure was being asserted as met at 0.331% (a near miss, not a match) via a tolerance constant mislabeled 0.3% but actually set to 0.5%; now reported honestly as not met, with the 15% level-agreement check (the one that actually gates the artifact) unaffected. The mix-shift TVD floor moves from 0.005 to 0.010 — a 200k-draw null simulation showed 0.005 sits at the 72nd percentile of pure switching noise, not a real discrimination threshold. Several minor doc inaccuracies (a switching-matrix cell, a crossover-count scope mismatch, a code comment's stale conversion count) are also corrected, and the community-gains-under-last-touch finding's generator-routing explanation is restated to lead with the caveat rather than follow it
- `quota_history`: ISR/AE quota is now back-solved from the opportunity generator's realized deal supply — opportunities closed per fully-ramped rep-quarter × that segment's realized win rate × average won deal size — instead of being drawn from ranges sized against `config.ACV_RANGES` with no reference to deal volume. `_QUOTA_BASE_RANGE` moves from AE $400–700K and ISR $150–220K per quarter to **AE $60–105K and ISR $22.5–33K**, each band's midpoint set so the *stated* quota (after the generator's existing ~2%/quarter step-up) lands on the measured anchor of $103,619 per ramped AE rep-quarter and $34,363 per ramped ISR rep-quarter; band half-widths and the step-up mechanic are unchanged. The old ranges implied ~2.6 wins per AE per quarter against an actual 0.35, and were unreachable by construction rather than by performance: total AE new-business pipeline across the whole simulation is 452 opportunities, so even at a 100% win rate the supply covers 54% of stated AE quota. Company-wide attainment moves from **12.9% to 84.4%** across the six-year history (94.8% over the fully-supplied window), and from no rep-year in six years reaching 100% (max 68.5%, median 9.4%) to **36.4% of rep-years at or above 100%**, median 75.7%. `analytics/capacity_planning.py`'s `quota_coverage_ratio` is consequently reclassified from `level_caveated` to `comparable` — coverage runs 0.565–0.969 against a prior 8.5–14.5%, and the achievability verdict is selective (34 of 48 team-quarters over the margin, against 48 of 48) rather than definitional. The level-immune `ramp_attributable_gap_pct` basis is unchanged at 13 of 48, as its level-immunity claim predicts. Adds a cross-generator regression check in `tests/test_phase1_batch2.py`, a `Rep/capacity` edge case and a distributional-realism band in `docs/acme-corp-phase1-data-qa-plan.md`, and restates the Capacity planning entry in `docs/acme-corp-analytics-methods.md` against the recalibrated figures
- Capacity planning's team-quarter aggregation now propagates a not-yet-estimable rep's `NaN` capacity to the whole team-quarter instead of silently dropping it from the sum, which previously fabricated a "zero capacity" reading for teams that simply hadn't accumulated enough baseline history yet in `prior_quarters_only` mode. The decomposition-reconciliation check now runs against both baseline modes, not only the default
- `gtm_plan_targets`: `expansion_consumption_revenue` and `contraction_churned_revenue` are now derived from the benchmark-blended `nrr`/`grr` anchors (`1 − grr**(1/12)`, and `nrr**(1/12) − 1 + that`, re-derived per plan year) instead of being set from standalone monthly shares of the revenue base. The standalone shares compounded to an annual GRR of ≈0.51 and NRR of ≈1.55 against plan rows stating ≈0.91 and ≈1.15, so the plan table stated the same identity two contradicting ways; the two halves now reconcile to machine precision. Adds a table-level regression check in `tests/test_phase1_batch5.py`, and restates the `nrr`/`grr` level-comparability caveat in `analytics/variance_diagnostic.py` and `docs/acme-corp-analytics-methods.md` to locate the remaining gap on the actuals side (gross contraction bucket scope) rather than in the plan generator

### Added
- Semantic layer / AI context layer (`semantic/`): an MCP server (`list_metrics`, `get_metric_definition`, `query_metric`) reading the dbt-built marts layer, backed by a metric registry deterministically parsed from `docs/acme-corp-gtm-metric-tree.md` (`semantic/build_registry.py`) rather than hand-maintained as a separate copy — stamped with a hash of the source tree so a registry regeneration is traceable to the tree version it was built from. `query_metric` computes ratio metrics (NRR, GRR, logo retention, win rate, avg initial commitment, onboarding completion/CS efficiency) as `SUM(numerator)/SUM(denominator)` across the requested grain rather than averaging pre-computed monthly ratios, so multi-period and multi-segment queries return exact rather than approximate figures. Whitelist guardrails reject unknown metric names (with fuzzy suggestions), the tree's two explicitly non-additive nodes, dimensions the tree doesn't specify for a given metric, dimensions the tree allows but the marts don't yet back, and invalid segment values — every successful query returns the metric's registry definition alongside its data. Requires Python 3.10+ for the MCP SDK; runs in a dedicated `semantic/.venv` (Python 3.12), separate from the rest of the project's Python 3.9 environment
- Data quality / metric governance (`analytics/data_quality_governance.py`): mechanizes the metric tree's parent-equals-function-of-children contract and this project's non-negotiable invariants into automated checks against the live dbt-built marts. Computationally verifies every computable metric-tree formula edge (sum/product/ratio, per the tree's own stated type) against real mart values; extends the Phase 1 QA plan's referential-integrity, completeness, distributional, and volume checks to the marts layer, which nothing previously re-checked post-transformation; and confirms segment values, the absence of segment-downgrade paths, all four migration `trigger_reason` values, and the not-independently-random relationships behind win probability, churn probability, and usage growth all hold in real generated data. A synthetic injected-violation test suite (a broken parent-sum, a broken ratio, a fabricated segment value, a fabricated downgrade path, a genuinely-random column) confirms the checks actually catch what they claim to, per its structural/logic-artifact shape — no accuracy target applies
- Forecast (`analytics/forecast.py`): reconciles four lenses on the same open-pipeline question — rep and manager bottoms-up roll-ups (weighted by a dollar-weighted, isotonically-ordered close rate per segment/opportunity-type/forecast-category, derived from realized outcomes rather than a flat accounting convention), a fitted win-probability classifier scored on deal mechanics the bottoms-up lenses never see, and the CRO overlay applied as a verbatim dollar delta with no fabrication where no override is logged. The classifier hits its pre-stated out-of-time AUC target at the canonical checkpoint and is reported, not hidden, when a second checkpoint's AUC exceeds the target band's ceiling. A lens-divergence flag surfaces periods where the four views materially disagree, backed by a real backtest showing each lens's own bias (the ML lens under-forecasts by ~12% under renewal-mix drift, which is the argument for keeping all four rather than collapsing to one)
- Marketing attribution & channel mix (`analytics/marketing_attribution.py`): derives per-lead touch sequencing from raw event timestamps (independently confirmed against each lead's own recorded source channel), four multi-touch attribution models (first-touch, last-touch, linear, time-decay), and a channel-mix-shift comparison across them, reported alongside — not blended with — a real experimental incrementality estimate from the generator's holdout cells. The two answer different questions: attribution is correlational and structurally can't score the largest channel (organic, which carries no holdout), while the causal estimate shows attribution overstates paid's contribution by ~35% relative to measured incremental lift. A generator-routing artifact in the cross-channel touch mechanism (community gaining share under last-touch despite the longest conversion journey) is identified and reported as a limitation rather than presented as a funnel-position finding
- Capacity planning (`analytics/capacity_planning.py`): rep-quarter attainment analysis and a ramp-adjusted capacity model for ISR/AE reps, decomposing the gap between stated quota and expected capacity into exact productivity, coverage, and ramp-mix components. The ramped-rep productivity baseline is derived from real attainment history, not invented, and the build spec's "~50% capacity for unramped reps" assumption is independently reconciled against the observed ramping/ramped ratio in the data
- `fact_forecast_submissions` and `cro_forecast_adjustments` (`generators/forecast.py`, `generators/run_batch6.py`): weekly Commercial/Enterprise forecast snapshots and CRO overlay adjustments. Rep and manager forecast categories are both driven by a shared, point-in-time win-propensity signal (stage, stage-relative stall, POC outcome, rep ramp status) rather than the eventual outcome, with the rep call carrying a real optimism bias and the manager call better calibrated — the resulting gap is itself predictive: opportunities where the manager downgrades a confident rep call close at a measurably lower rate than opportunities where the two agree. CRO adjustments trace to each segment/period's real pipeline-coverage ratio rather than an independent draw. Validated by a 52-check suite (`tests/test_phase1_batch6.py`)
- `campaigns`, `leads` and `campaign_engagement_events` (`generators/marketing_funnel.py`, `generators/run_batch7.py`): the marketing-automation funnel at raw touch grain, splitting the parent `inbound_marketing` acquisition channel into the metric tree's organic/content, paid, and community/events sub-channels. Every inbound-sourced account is explained by exactly one converting lead created strictly before its signup; non-converting lead volume is sized off a stated per-sub-channel conversion rate and drawn from `market_universe`'s non-customer population. Touch volume and recency drive conversion rather than accompanying it, multi-campaign and cross-sub-channel touch paths exist so multi-touch attribution has a real path to attribute, and the three sub-channels are statistically distinct across conversion rate, touch volume, lead-to-signup gap, CAC, and lead-score distribution. Holdout cells run in paid and community across three quarters as genuinely suppressed control groups — treatment withheld, budget withheld, conversion at ~35% of the treated rate — giving incrementality testing a real excluded group. Validated by a 65-check suite (`tests/test_phase1_batch7.py`) covering structural integrity in both directions, point-in-time safety, distributional bands, and both causal-wiring relationships
- Weekly executive readout (`analytics/weekly_readout.py`): assembles the variance-diagnostic engine's output into the build spec's readout structure — header, all 11 Layer-1 nodes grouped by pillar, variable-length drill-downs, and the health-score watchlist — and renders it as a Markdown deliverable under `analytics/outputs/`. Performs no business computation; every figure traces field-by-field to the artifact that owns it, verified by a 20-check structural/trace/rendered-document suite. Executive-summary narrative generation, automated playbook triggers, and forecast are carried as explicitly-statused sections rather than omitted or fabricated, with `assemble_readout()` as the structured seam a narrative step consumes
- Variance-diagnostic engine (`analytics/variance_diagnostic.py`): for any Layer-1 metric, computes variance from plan (or, for Activation, from a trailing baseline) and identifies the true outlier Layer-2 child among its tree siblings, with Layer-3 evidence surfaced where the branch and available marts support it. Enforces the metric tree's real layer structure programmatically — a node's layer is read from a single frozen tree definition, never assigned at emit time — and validated against a synthetic test suite with known-correct answers rather than a statistical accuracy target, per its structural/logic-artifact shape
- `gtm_plan_targets`: FP&A/RevOps plan values for ten of the metric tree's eleven Layer-1 nodes, generated on an annual planning cycle grounded in the QA plan's benchmark reference table and independently of any other generator's realized output (`generators/gtm_plan.py`), exposed through `stg_gtm_plan_targets` and `mart_gtm_plan`. Activation carries no plan row by design — the readout reports it against a trailing baseline instead
- Segment/segmentation migration analysis (`analytics/segment_migration.py`): migration velocity and trigger-reason mix by segment pair, time-in-prior-segment distribution, and graduated revenue, reconciled against `mart_growth_bridge`'s independently-computed migration MRR to floating-point precision
- Statistical validation package for Phase 4 predictive models (coefficients, confusion matrix at the production operating threshold, calibration check, relative input-importance breakdown, model-choice rationale), applied to the account health score and captured as a standing requirement in `analytics-engineering-conventions` and `analytics-model-builder`/`analytics-model-validator`
- `asset-brief-writer`'s "Technical validation" appendix section, reproducing a model's statistical validation package for a stats-literate reader alongside the plain-language brief
- Commit-msg githook enforcing Conventional Commits format and the repo's process-language restrictions, activated via `git config core.hooksPath .githooks`
- `fact_model_performance_history`: append-only log of Phase 4 model-eval checkpoints, backed by a version-controlled CSV and a Python logging helper (`analytics/model_performance.py`)
- `docs/acme-corp-analytics-methods.md`: methodology, validation target, and drift threshold reference for every Phase 4 artifact
- `analytics-model-builder`, `analytics-model-validator`, and `drift-monitor` agents for building, validating, and monitoring Phase 4 artifacts
- Initial repository scaffold: company model, GTM motion mechanics, metric tree, and Phase 1 data QA plan
- Three-segment GTM model (SMB, Commercial, Enterprise) with firmographic entry scoring and usage-based migration
- Consumption-based revenue model with a three-pillar diagnostic metric tree (Growth, Efficiency, Durability)
- Sample weekly executive readout demonstrating the tree's variance-diagnostic drill-down capability
- 22-artifact analytics portfolio plan with dependency-ordered build sequencing
- Phase 1 data generation QA plan: edge cases, grounding benchmarks, and test suite
- Claude Code project configuration (`CLAUDE.md`) and skill/agent set for dbt modeling, semantic layer construction, and repo hygiene
